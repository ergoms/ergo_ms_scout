# SCOUT — инструкции для работы над модулем

Область: весь репозиторий Scout, в ERGOMS — `modules/scout/`. Соблюдать также инструкции родительского репозитория.

## Текущий этап

Сейчас пользователь продумывает структуру и документацию. Обсуждение возможности не означает поручение писать код, поднимать контейнеры или запускать демонстрации. Прямой запрос на реализацию меняет объём работы в рамках этого запроса; повторное разрешение на уже порученное действие не требуется.

Подключение дополнительных машин оставлено на будущее. Docker-пример удалён; не восстанавливать его как часть обсуждения архитектуры.

Две команды: FRONTEND отвечает за UX, дизайн и клиент; SYSTEM — API и остальную систему. Базовые ручной и визуальный сценарии уже реализованы. Для инспектора сервер API-004 реализован и проверен; FRONTEND ведёт UX-004, затем DES-006 и FE-005, SYSTEM сопровождает интеграцию. Старые задачи не начинать заново. Границы файлов и передача описаны в `docs/TEAM_WORKFLOW.md`; читать чужой код можно, незаметно менять чужую область внутри своей задачи нельзя.

## Как вести проектирование

- Отделять подтверждённое требование, техническое предложение и факт из кода. При конфликте учитывать последнее прямое уточнение пользователя.
- Сначала разъяснять непонятный термин на примере, затем уточнять выбор. Не повторять уже закрытые вопросы.
- Новое решение записывать в `docs/DECISIONS.md`, связанные требования — в `BEHAVIOR.md`; закрывать соответствующий вопрос и уточнять backlog.
- Обсуждение задачи не переводит её в выполненные. Для завершённой реализации нужны код и проверка её результата.
- Не создавать второй файл с теми же требованиями или альтернативный backlog. Документы первоначального исследования считать историческими, как указано в карте документации.
- Не обещать универсальный разбор или производительность без проверок на согласованном наборе.

## Границы и обязательные свойства

- Ближайший источник — открытый HTML; другие загрузчики и форматы оставлять расширениями.
- Три способа настройки ведут к общему плану: ручные CSS/XPath, выбор полей кликами и описание цели с LLM.
- LLM предлагает схему, правила и план; после подтверждения извлечение выполняется без модели.
- Основной сбор начинается только после подтверждения хеша версии плана. Одновременно выполняется один сбор.
- Повторная задача и запоздалая попытка не создают повторные записи. Завершение определяется состоянием в БД, а не пустотой брокера.
- Снаружи использовать `public_id`, для владельца — `user_public_id`. Чужие модели не импортировать; интеграции идут через мост ядра.
- Не выполнять многочасовой обход одной задачей Celery. Прокси — сетевой посредник; дополнительная машина — исполнитель задач.

## Код и проверки

Координатор — `api/services/runs.py`, диспетчер и обработчики — `api/services/tasks_exec.py`, план — `api/services/plan.py`, страница — `client/components/ScoutPage.vue`.

При порученной реализации использовать команды платформы; тесты модуля: `ergoms api test modules.scout.api`. Для изменений только документации проверить ссылки, согласованность и diff; службы ради этого не запускать.

Коммитить и отправлять изменения в пределах поручения. Сообщения — по-русски, 1–3 предложения, формат `<type>: <описание>` без scope; без `Co-authored-by`.
