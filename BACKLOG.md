# SCOUT — backlog

Актуализировано 9 ноября 2026 года. Этот файл — единственный список задач. Для проверенных участков указан объём приёмки; новые требования и оставшаяся работа не отменяют уже выполненное. Для UX-004 подготовлен экспериментальный прототип взаимодействия на действующем редакторе; продуктовый FE-005 не считается завершённым.

Существующий HTML-сценарий не нужно создавать заново: его состояние описано в [IMPLEMENTATION_STATUS.md](docs/IMPLEMENTATION_STATUS.md). Подтверждённые решения — в [DECISIONS.md](docs/DECISIONS.md), нерешённые вопросы — в [OPEN_QUESTIONS.md](docs/OPEN_QUESTIONS.md).

Статусы задач — **к обсуждению**, **согласовано для реализации**, **в работе**, **проверено**, **отложено**. По умолчанию задача имеет статус «к обсуждению». Статус «проверено» требует результата и указания проверки. Исторический эксперимент сам по себе не закрывает будущую задачу.

Ручной пошаговый клиент влит в `dev`, UX-003 принят заказчиком для ручного сценария. Базовый визуальный выбор UX-001/API-002 также реализован и проверен на живом API; сервер дерева DOM доступен, экспериментальный прототип UX-004 ожидает пользовательского прохода. Серверные AI-001, SPEC-004 и API-003 доступны, их клиентское подключение остаётся работой FRONTEND. [Фактическое состояние](docs/IMPLEMENTATION_STATUS.md).

Ближайший цикл визуального редактора: **UX-004 → DES-006 → FE-005 → FE-004**. SYSTEM реализовал и проверил **API-004**; FRONTEND использует его в FE-005, уточнения контракта передаёт SYSTEM. Существующий UX-001 не начинать заново. Остальные клиентские участки вести в FE-001–FE-003, без второго списка задач.

Две команды: **FRONTEND** делает только клиент и дизайн; **SYSTEM** — API и всю остальную часть системы. У каждой задачи один ответственный; вторая команда участвует в обсуждении и принимает результат через контракт. Границы и порядок передачи — в [TEAM_WORKFLOW.md](docs/TEAM_WORKFLOW.md), задания команд — [FRONTEND](docs/teams/FRONTEND.md) и [SYSTEM](docs/teams/SYSTEM.md). Отдельные backlog для команд не создаются.

## Сначала: структура и требования

### SPEC-001 — согласовать общую модель задания и результата

Ответственный: **SYSTEM**. FRONTEND проверяет представление полей, ошибок и общего плана в интерфейсе.

Определить источник, тип страницы, поля результата, правила извлечения, версию плана, запуск и задачу. Сопоставить их существующим `Job`, `JobRevision`, `Run`, `Task`, `PageSnapshot`, `Record` и `Evidence`; не вводить новые сущности без описания их ответственности.

Готово для реализации, когда есть один пример задания и результата, определены типы и обязательность полей, а ручная, визуальная и текстовая настройка приводят к одному плану. Связанные вопросы: Q-001 и Q-002.

Серверные профили идентичности по SKU, выбранному текстовому полю и конечному URL страницы реализованы. Прежний SKU сохраняет алгоритм ключа; новые профили включаются явно. Без надёжного значения наблюдения остаются раздельными, совпадение названий не объединяет объекты. URL-профиль требует одну запись на страницу. Предпросмотр, история цен, сравнение и Evidence используют общий механизм. Настройка профилей в клиенте остаётся отдельным этапом FRONTEND. [SPEC-001](docs/API_CONTRACT.md#spec-001--идентичность-товара) · [Профили без SKU](docs/API_CONTRACT.md#явные-ключи-без-sku)

### SPEC-002 — описать этапы сбора и правила по типам страниц

Ответственный: **SYSTEM**. FRONTEND участвует в выборе пользовательских этапов и переходов.

Разделить обнаружение URL, загрузку, сохранение снимка, извлечение, проверку и экспорт. Обсудить, как одним заданием описывать каталог и страницы объектов с разной разметкой.

Готово для реализации, когда понятны входы и выходы этапов, выбор правил для страницы, предпросмотр и поведение при отсутствии совпадений. Связанный вопрос: Q-003.

Серверный этап **проверен**. На живом стенде подтверждены предпросмотр, конфликты типов, сбор каталога с Evidence, выгрузки и совместимость старого плана. Настройку типов в интерфейсе согласовать с FRONTEND. [Контракт SPEC-002](docs/API_CONTRACT.md#spec-002--правила-для-типов-страниц)

### SPEC-003 — определить смысл цели «до 10 000 страниц»

Ответственный: **SYSTEM**. FRONTEND использует согласованные счётчики и ограничения.

Различить найденные URL, попытки загрузки, успешно сохранённые страницы и полученные записи. Определить ограничения времени, объёма, частоты запросов и памяти, а также ожидаемое поведение частичного результата.

Базовый этап выполнен. [SPEC-003](docs/SPEC_003.md) фиксирует счётчики, критерии полноты, воспроизводимый каталог и замеры. По выбору заказчика сначала измеряем фактические время, память и полноту без требования к скорости. Профиль реальных источников и допустимые ресурсы остаются в Q-004, расширенные прогоны относятся к SCALE-001. Рабочий предел — 200 адресов.

### SPEC-004 — выбрать модель настройки прокси

Ответственный: **SYSTEM**. FRONTEND проектирует форму по согласованным полям и ошибкам.

Уточнить протоколы, формат ввода, один профиль или список, привязку к заданию и поведение при ошибке. Секреты не помещать в журнал, экспорт и показанный план. Ротация прокси и обход блокировок не считаются подтверждёнными требованиями.

Серверный этап реализован и проверен на тестовом HTTPS-прокси. API хранит версии профиля, воркер проверяет оба TLS-соединения и назначение `CONNECT`, а при отказе останавливает новые загрузки. Подключение формы и выбора профиля относится к FE-001. [Контракт SPEC-004](docs/API_CONTRACT.md#spec-004--профили-прокси)

Режим без авторизации реализован через `auth_type: none` без полей логина и пароля; прежний ввод сохраняет `basic`. Миграция `0015` сохраняет старые версии. На тестовом TLS-прокси проверены отсутствие заголовка авторизации, `407` без прямого обхода, строгий ввод, смена режима, защита от подмены режима в БД, ротация ключа и отзыв. Полный серверный прогон — 166 тестов. Для формы FE-001 добавляется выбор `basic` / `none`; `credentials_configured: false` не означает недоступность узла.

Живая приёмка HTTPS-прокси без реквизитов **проверена** на рабочем проекте: открытый узел дал 20 записей и 40 Evidence, совпавших с прямым сбором. Внутренние адреса и чужой профиль заблокированы, рабочий предел 200 сохранён. Открытые узлы также отдавали `407`, поэтому стабильный поставщик для эксплуатации не выбран. Шесть прежних SOCKS5-прокси не переносились, поддержка SOCKS5 не добавлялась. [Результаты](docs/IMPLEMENTATION_STATUS.md#https-прокси-без-авторизации) · [Q-005](docs/OPEN_QUESTIONS.md#q-005--какие-прокси-и-как-ими-управлять)

Готово для реализации, когда описаны поля, проверки, хранение реквизитов и ошибки. Связанный вопрос: Q-005.

## UX и дизайн: от сценария к макетам

Разработка взаимодействия — в [UX.md](docs/UX.md), оформление — в [DESIGN.md](docs/DESIGN.md). UX-003 проверен для ручного сценария; базовый UX-001 реализован. Для остальных задач не заявляется приёмка всех макетов. UX-002 и DES-001–DES-005 сохраняют исходные идентификаторы и описывают основу: менять в них только затронутые сценарии, а не повторять весь этап. Новое развитие выбора блоков выделено в UX-004, DES-006 и FE-005. Новые задачи имеют статус **к обсуждению** до приёмки взаимодействия и контракта; само требование показать DOM-дерево и улучшить выбор подтверждено заказчиком.

### UX-002 — сценарии пользователя и структура взаимодействия

Ответственный: **FRONTEND**. SYSTEM участвует в сверке данных, ограничений и состояний.

Уточнить, кто и с какой целью использует Scout, входные данные, критерий нужного результата, основные шаги, ошибки и возвраты. Описать три способа настройки, предпросмотр, подтверждение, управление сбором и работу с итогом без привязки к цветам и расположению кнопок.

Результат: сценарии с условиями начала и завершения, картой действий и вопросов пользователя; отдельно отмечены гипотезы. При уточнении новых сценариев использовать известные требования, неизвестное вынести в Q-009. Модель и возможности сверять со SPEC-001 и SPEC-002, не ждать готовности всего сервера.

### DES-001 — схемы экранов на основе UX

Ответственный: **FRONTEND**. SYSTEM проверяет соответствие возможностям и состояниям API.

По сценариям UX-002 определить области ближайшего интерфейса: настройка, предпросмотр, выполнение, результат; отдельно решить необходимость обзора заданий и истории. Разместить основные данные и действия, показать переходы, возвраты и сохранность черновика в схемах экранов.

Результат: схемы экранов и переходов без детальной стилизации, связанные с пользовательскими сценариями. Зависит от UX-002; данные и состояния сверяются со SPEC-001 и SPEC-002. Визуальное направление уточняется в Q-008.

### DES-002 — настройка тремя способами

Ответственный: **FRONTEND**. SYSTEM предоставляет форматы плана и требования проверки.

Спроектировать ручные поля и селекторы, визуальный выбор, описание цели с LLM и их переключение. Показать общий план, связь выбранной карточки с полями, совпадения и исправления на других примерах.

Результат: макеты каждого способа с пустым, заполненным и ошибочным состоянием; понятное поведение правок при переключении. Зависит от DES-001 и решения о типах страниц. Базовый визуальный выбор выполнен в UX-001; новый инспектор проектируется в UX-004/DES-006 и реализуется в FE-005. Сервер модели — AI-001, клиент модели — FE-001.

### DES-003 — предпросмотр и подтверждение

Ответственный: **FRONTEND**. SYSTEM подтверждает контракт предпросмотра и переходов запуска.

Спроектировать примеры записей, происхождение полей, пропуски, границы сбора и возврат к исправлению правил. Пользователь понимает содержание подтверждаемого плана; основное действие одно.

Результат: макеты успешного, пустого и частичного предпросмотра, ошибок источника и изменённого плана. Учитываются правила возврата и запоздалого ответа из BEHAVIOR.md. Зависит от DES-001 и DES-002.

### DES-004 — выполнение и результаты

Ответственный: **FRONTEND**. SYSTEM предоставляет счётчики, ошибки, результаты и экспорт.

Спроектировать раздельные счётчики загрузки и разбора, паузу, продолжение, отмену, потерю связи, журнал в подробностях и итоговую таблицу с происхождением и выгрузкой. Доступ ко всем строкам не должен сводиться к первым двадцати.

Результат: макеты активного сбора, переходных состояний, успеха, частичного результата и ошибки с доступными действиями. Работа с большим результатом зависит от SPEC-003 и SCALE-001.

### UX-003 — проверка прототипа взаимодействия

Ответственный: **FRONTEND**. SYSTEM проверяет, что сценарии опираются на определённые состояния и данные.

Статус — **проверено для ручного сценария**. По сообщению заказчика проверка прошла без замечаний.

Пройти прототип с заказчиком или доступным будущим пользователем: первый сбор, исправление предпросмотра, выбор способа настройки, пауза/отмена, возвращение на страницу и понимание результата. Формат и участников проверки согласовать отдельно; не придумывать проведённые интервью или измерения.

Результат: записанные наблюдения, непонятные шаги, изменения прототипа и оставшиеся вопросы. Зависит от UX-002 и DES-001–DES-004. Проверка касается взаимодействия; детальная визуальная стилизация может ещё отсутствовать.

### DES-005 — визуальная основа, компоненты и проверка макетов

Ответственный: **FRONTEND**.

Согласовать визуальное направление, формат макетов и поддерживаемые размеры экрана. Определить использование оболочки и компонентов ERGOMS, подписи полей, фокус, клавиатурные действия и представление ошибок. Новая палитра и отдельная библиотека пока не выбраны.

Результат: согласованные визуальные макеты ключевых состояний, перечень используемых компонентов ядра и замечания, которые нужно закрыть перед реализацией. Зависит от DES-001–DES-004, UX-003 и Q-008; не закрывается одним изображением основного экрана.

### UX-004 — выбор блоков и навигация по DOM

Ответственный: **FRONTEND**. Статус: **в работе: экспериментальный прототип и технический проход подготовлены; пользовательская проверка ожидается**. Направление подтверждено заказчиком. SYSTEM проверяет доступность данных и безопасность API-004. Прототип `/scout/ux-004` развивает существующий редактор и использует API-002/API-004; сценарий и наблюдения — в [UX.md](docs/UX.md#прототип-ux-004-от-9-ноября-2026-года). DES-006/FE-005 этим не закрыты.

Спроектировать продолжение работающего UX-001: наведение показывает будущий выбор, клик фиксирует блок; отдельно видны карточка записи, активное поле и остальные совпадения. Связать снимок, раскрываемое DOM-дерево и цепочку родителей в обе стороны. Пользователь может перейти к родителю, дочернему или соседнему узлу, увидеть примеры значения и исправить слишком широкий селектор до принятия. Техническую структуру можно свернуть, не теряя выбранный блок.

Результат: сценарии и кликабельный прототип на Books to Scrape и локальном каталоге с вложенными ссылками/пустым полем. Пройти выбор карточки, названия и цены, исправление общего `a` на точное правило, ноль/несколько совпадений, выбор с клавиатуры, смену снимка и узкий экран. Замечания и решения записать в UX.md; пользовательскую проверку не считать уже проведённой. Готово к DES-006, когда понятны выбор, отмена чернового выбора, принятие правила и возврат без потери полей. Общий предпросмотр и подтверждение запуска сохраняются.

### DES-006 — визуальное оформление инспектора блоков

Ответственный: **FRONTEND**. Статус: **к обсуждению**. Зависит от UX-004; использует основу DES-005.

Оформить единое рабочее место: DOM-дерево, безопасный снимок и инспектор карточки/поля с примерами. На широком экране предложить три изменяемые по ширине области; на узком — переключаемые представления без потери выбора. Подготовить макеты наведения, выбранного блока, совпадений, пустого/ошибочного состояния и истёкшего снимка. Различать состояния не только цветом, использовать темы и компоненты ERGOMS, видимый фокус и читаемые короткие подписи. Декоративная анимация не должна мешать попаданию в элемент.

Результат: согласованные ключевые состояния в светлой/тёмной теме, состав компонентов, размеры и поведение панелей. Красивое оформление относится к самому редактору: исходные стили и внешние ресурсы сайта не возвращаются в снимок. Не создавать новую библиотеку или копию редактора без необходимости. Подробности — DESIGN.md.

## Общая граница: API и передача данных

### API-001 — согласовать контракт между командами

Ответственный: **SYSTEM**. FRONTEND проверяет достаточность контракта для DES-001–DES-004.

Актуализировать [API_CONTRACT.md](docs/API_CONTRACT.md) по коду, затем описать выбранные расширения: запросы, ответы, идентификаторы, типы, состояния, ошибки и совместимость. Передать примеры основного, пустого, ошибочного и частичного результата.

Готово для реализации сценария, когда обе команды используют один формат и понятно, какие операции уже работают, а какие только проектируются. Зависит от SPEC-001 и SPEC-002. Строки и действия интерфейса не должны опираться на несуществующие поля.

### API-002 — серверная граница визуального выбора

Ответственный: **SYSTEM**. FRONTEND — потребитель для UX-001.

Статус: **проверено для базового визуального выбора**. Работают загрузка/опрос временного снимка, изолированный HTML, `data-scout-node`, проверка CSS и предложения по `node_id`, примеры и ошибки. Старый формат сохраняется. [Контракт API-002](docs/API_CONTRACT.md#api-002--серверный-черновик-для-ux-001) · [Приёмка UX-001](docs/IMPLEMENTATION_STATUS.md#ux-001--клиент-визуального-выбора).

Исходные классы/атрибуты и полноценное дерево API-002 не возвращает. Это расширение API-004, а не причина заново объявлять API-002 неготовым.

### API-003 — выдача больших результатов и контракт выгрузки

Ответственный: **SYSTEM**. FRONTEND — потребитель для FE-003.

Сервер выдаёт строки с Evidence порциями по `limit` и `cursor`, а счётчики для опроса прогресса — по `summary=1`. JSON и CSV формируются порциями и сохраняются через Media API. Запросы текущего клиента возвращают прежний формат. [Контракт](docs/API_CONTRACT.md#порции-результата-и-опрос-прогресса)

Для перехода таблицы и опроса прогресса на новый режим FRONTEND использует описанный контракт. Проверка предельного объёма остаётся в SCALE-001.

### API-004 — безопасные данные дерева для визуального инспектора

Ответственный: **SYSTEM**. Статус: **проверено для серверного контракта v1**. FRONTEND — потребитель для FE-005; его интеграция ещё не выполнена.

Миграция — `0014_retention_cleanup`, [результаты](docs/IMPLEMENTATION_STATUS.md#scale-001--очистка-по-срокам). Клиент управления хранением остаётся отдельной задачей FRONTEND в FE-003.

### REL-001 — проверить восстановление и целостность

Ответственный: **SYSTEM**. Клиентские переходы и запоздалые ответы отдельно проверяет FRONTEND в FE-004.

## Защиты источников: исследование и прохождение проверок

Scout распознаёт известные страницы проверки до сохранения снимка. Исследование способов прохождения Cloudflare ведётся в ANTI-001. Работа по прохождению CAPTCHA Яндекса приостановлена в ANTI-002.

Общие границы: отличать проверку от страницы результата, ошибки доступа/сети и отказа прокси; не создавать Record из заглушки CAPTCHA даже при HTTP 200. Предусмотреть ограниченное ожидание, попытки и частоту, паузу/отмену и восстановление без дублей. Пользовательское ожидание не держит долгую задачу Celery или блокировку БД. Внешние сервисы и облачные модели распознавания запрещены решением заказчика; не отправлять им картинки, HTML или сессии. Cookies/токены и браузерный контекст принадлежат владельцу/источнику, имеют срок и не попадают в API, план, логи, Evidence, выгрузки или сообщения Celery.

Браузерный способ исследовать отдельно от HTML-снимка API-002/API-004: внешний JavaScript нельзя включать в DOM-инспектор. Нужны изолированная сессия без личного профиля пользователя, сетевые границы всех запросов/редиректов/подресурсов, запрет внутренних адресов и проверяемый TLS. Привязку сессии к источнику и выбранному прокси сохранять; смена сетевого выхода и ротация не становятся скрытым действием. Состояния ожидания и ручного продолжения для FRONTEND проектировать в FE-002 после серверного контракта; они не блокируют текущий FE-005. Рабочий предел остаётся **200 страниц**.

### ANTI-001 — обход проверок Cloudflare при сборе

Ответственный: **SYSTEM**. Статус: **в работе, автоматическое прохождение не готово**. FRONTEND участвует в сценарии ожидания/продолжения через FE-002; общие вопросы — Q-010.

Исследовать Cloudflare Challenge Pages, Turnstile и обычный отказ доступа как разные случаи. Обнаружение по `cf-mitigated: challenge` и известным признакам HTML уже реализовано; одного HTTP 403 или упоминания Cloudflare в тексте недостаточно. На выбранном источнике проверить прохождение в браузерной сессии и возможность автоматизации без внешнего сервиса. Текстовое ML-распознавание не получает токен Turnstile и не заменяет проверку браузера. Определить способ передачи успешного контекста загрузчику и повторной проверки целевой страницы, истечение/сброс сессии, предел ожидания и понятный отказ. Полученный токен сам по себе не считается загруженной страницей.

Первый результат: подтверждённый тип защиты, выбранный способ и серверный контракт с границами успеха; затем реализация на согласованном наборе. Для приёмки нужны защищённая и обычная страница, ложное срабатывание, успешное продолжение с корректными записями, повторная проверка/истечение, отказ, пауза/отмена и повторная доставка без дублей. Зафиксировать время/число попыток и ресурсы локальной модели; не обещать универсальную поддержку всех сайтов Cloudflare.

Основа исследования: [Challenge Pages](https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/), [признак ответа Challenge](https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/), [Turnstile](https://developers.cloudflare.com/cloudflare-challenges/challenge-types/turnstile/).
