Это не приёмка сетевой загрузки локального источника. Общий `a` с пустой ссылкой исправляется через родительский заголовок либо CSS `h3 a`; настраиваются название/цена, различаются пустое и отсутствующее значение, проверяются поиск, отмена, клавиатура, темы и переключение областей. Для совместимости локального стенда применены существующие миграции Scout `0012`–`0016` в рамках ранее разрешённого обновления базы; новые миграции или серверный код не добавлялись.

Актуальные цели находятся в [DECISIONS.md](DECISIONS.md). Реализованы ручные селекторы, визуальный выбор полей и HTML-обход до 200 страниц. Клиент поддерживает отдельное подтверждение плана. - Шесть этапов: режим → источник и правила → предпросмотр → подтверждение → сбор → результат. Подтверждение доступно только для загруженного задания, совпадающего хеша плана и неизменённого черновика с непустым предпросмотром.
- На первом экране представлены три режима. Ручной и визуальный режимы работают с API; предложение ИИ ещё не подключено к клиенту. Переход к ручным правилам сохраняет адрес и принятые поля.

- Настройки системы открываются через существующий интерфейс ядра; правила и ограничения сбора находятся в задании. Светлая, тёмная и автоматическая темы используют механизм и цветовые переменные ERGOMS.
- Форма, подтверждение и результаты адаптированы к узким экранам. Результаты используют DataTable ядра, клиентскую пагинацию всего полученного массива и просмотр происхождения поля; значения 0 и false сохраняются.
- Настройка с ИИ и серверные порции результатов остаются задачами AI-001 и API-003.

Проверки клиента запускаются из корня ERGOMS: `ergoms npm --prefix=../../modules/scout/client run test:workflow` и `ergoms npm --prefix=../../modules/scout/client run test:browser`. Браузерная проверка собирает настоящие компоненты с явно тестовым API в локальную HTML-страницу в `virtual_env/cache/tmp/scout-client-browser`; она не проверяет живой Django/Celery. Общие проверки: `ergoms npm run lint:check` и `ergoms npm run build`.

Перед слиянием на коммите [`c7828bd`](https://github.com/ergoms/ergo_ms_scout/commit/c7828bd1f8f62f8d1fdd7ee1fe75d022c1cec464) прошли 7 модульных тестов, ESLint для Scout и браузерный сценарий на закреплённой версии клиентского ядра ERGOMS. ## Сделано

Фазы 0 и 1: модуль `scout` в `modules/scout`.

- Приложение Django, права `scout_view`, `scout_configure`, `scout_run`, `scout_review`, `scout_export`, страница `/scout`, пункт меню.
- Задание, версия плана, запуск, задача, попытка, снимок страницы, версия схемы, версия правил, запись, доказательство поля, файл выгрузки.
- Предварительная загрузка HTML в `virtual_env/cache/scout/snapshots/`.
- Правила CSS и XPath по сохранённому снимку. CSS в этой версии: тег, класс, идентификатор, вложение и прямой потомок. Селекторы с атрибутами, запятой и псевдоклассами отклоняются.
- Сервер отклоняет основной сбор, если план этой версии не подтверждён.
- Одновременно допускается один незавершённый сбор.
- Извлечение идёт задачей Celery. Повтор с тем же снимком и теми же правилами не создаёт вторую запись.
- Просроченная аренда задачи возвращает её в очередь и не удаляет запуск.
- Поздний ответ старой попытки не записывает результат.
- JSON и CSV пишутся через media_api, клиент получает подписанную ссылку.
- Команды `ergoms scout:collect` и `ergoms scout:approve-run`.
- После сохранения задания форма снова читает название, адрес и поля по `?job=`.
- У запуска есть журнал. Если снимок уже лежит на диске, строки журнала считаются по этому файлу, а не по старым сообщениям.
- Ответ `gzip` и `deflate` распаковывается до записи снимка. Уже сохранённый файл с сигнатурой gzip при чтении тоже становится HTML. Селектор смотрит распакованную страницу.
- «Подтвердить план» и «Начать сбор» активны только пока запуск в статусе `awaiting_confirmation`. На завершённом запуске эти кнопки ничего не делают. Новую загрузку начинает «Загрузить страницу».
- Запись строится по селектору карточки. Поле карточки читается внутри неё, пустое значение не сдвигает следующую карточку. Без селектора карточки на странице одна запись. «Сохранить изменения» правит текущее задание, «Новое задание» начинает другое.
- Паузу можно продолжить. Просроченная аренда во время паузы или отмены доводит запуск до `paused` или `cancelled` и не оставляет его в переходном состоянии.
- Повтор задачи будит очередь сам и раз в 30 секунд через расписание Beat. Ключ загрузки — хеш адреса, не сам адрес. Локатор доказательства не ограничен 500 символами.
- XPath `string()` и `count()` дают одно значение, а не разбор строки по символам. Кодировка берётся из BOM, charset ответа, meta и запасного варианта utf-8, затем cp1251.
- «Получить предпросмотр» сохраняет план и готовит пример результата. Подтверждение и старт находятся на отдельном этапе; сервер проверяет хеш плана. По умолчанию собираются только указанные страницы. Режим «Обойти сайт» после подтверждения идёт по ссылкам в пределах сайта, глубины и потолка страниц. Загрузка, обход ссылок и извлечение — разные задачи. Журнал лежит в «Подробностях выполнения».

13 октября 2026 проверены глубина после редиректа, повторная постановка при обнаружении более короткого пути и совпадение границ обхода для кириллического домена и punycode. После перезапуска воркер повторил прежние 14 сценариев и новые случаи редиректа, цепочки и короткого пути. Полный `ergoms api test modules.scout.api --full --noinput` тогда остановился на миграции CRM. Подробности того прогона в [PHASE_2A_REPORT.md](PHASE_2A_REPORT.md).

Воркер подхватывает код карточек и распаковки только после перезапуска `ergoms start-worker --module=scout` или задачи `start-worker --worker=all`. `ergoms stop` останавливает службы. Закрытие Cursor — нет.

## REL-001 — восстановление сбора на живом воркере

6 ноября 2026 на `c1da0de` проверен обход сайта через HTTP API Django, отдельные процессы Celery и Beat и временную базу PostgreSQL. Для брокера использовалась отдельная SQLite. Контрольный каталог состоит из стартовой страницы и страницы по ссылке. Контрольный сбор дал две сохранённые страницы и три записи. Для имитации сбоя HTTP-сервер задерживал ответ второй страницы, пока воркер не был принудительно остановлен. Использовались штатные 120 секунд аренды и проверка Beat каждые 30 секунд.

- После остановки первая попытка получила `lease_lost`. Новый воркер повторил загрузку, сбор завершился в `completed` с теми же двумя снимками и тремя записями.
- Во время повторной загрузки второй живой воркер получил дубликат сообщения и вернул `changed: false`. Повтор старого сообщения после завершения также оставил записи и снимки без дублей.
- При сбое в `pausing` просроченная попытка получила `lease_lost`, а запуск перешёл в `paused`. Загрузка возобновилась по команде «Продолжить» и завершилась с теми же двумя снимками и тремя записями.
- При сбое в `cancelling` запуск перешёл в `cancelled`, потерянная загрузка больше не выдавалась. В отдельном прогоне воркер получил запоздалый HTTP-ответ уже после команды отмены. В обоих случаях сохранились только снимок и запись, созданные до отмены.

На свежем ядре ERGOMS эти сценарии повторены со штатным запуском отдельных воркеров Scout и `SCOUT_WORKER_DB_REUSE_MAX=50`. Beat восстановил потерянную задачу после 120 секунд аренды. После возобновления паузы сбор вернул те же три записи и два снимка. При отмене после падения и при позднем ответе живого воркера сохранились одна ранее записанная строка и один снимок. Воркеры проигнорировали повторную доставку во время новой попытки и сообщение от первой попытки после завершения. Замеры подключения к PostgreSQL приведены в [SPEC-003](SPEC_003.md#проверка-штатного-запуска-воркеров).

После объединения запросов диспетчера REL-001 повторён на живых Celery, Beat и PostgreSQL. Сбор восстановился без дублей, продолжился после паузы и сохранил только уже записанные данные при отмене и позднем ответе. В журнале Beat подтверждён 30-секундный интервал. Замеры приведены в [SPEC-003](SPEC_003.md#объединение-запросов-диспетчера).

При обновлении проекта примените миграцию `scout.0008_run_dispatch_requested_until` командой `ergoms db-migrate` перед запуском обновлённых Django и воркеров Celery.

## SPEC-004 — серверные профили HTTPS-прокси

Профиль хранит логин и пароль как шифротекст с отдельным ключом. Предпросмотр, основной сбор и визуальные снимки закрепляют конкретную версию профиля. На тестовом HTTPS-прокси проверены `CONNECT` к выбранному IP, TLS к источнику, 407, недоступность и запрет внутренних адресов и редиректов. Контрольные логин и пароль отсутствовали в ответах API, логах и опубликованных сообщениях Celery. Все 80 тестов Scout прошли. Настройки включения и миграция `0011` описаны в [SPEC-004](API_CONTRACT.md#spec-004--профили-прокси).

До расширения без авторизации внешний профиль не был включён. 7 ноября по указанию заказчика найдены шесть прокси из прежнего сборщика и их локальные настройки. Они использовали SOCKS5 на порту 8000; текущий контракт Scout поддерживает HTTPS-прокси. TCP-соединения открываются, но проверки приветствия SOCKS5, HTTP CONNECT и TLS завершились таймаутами на всех шести адресах без отправки реквизитов. Причина не установлена; считать это отказом пароля или истечением подписки нельзя. Секреты в рабочую БД Scout не переносились. [История выбора Q-005](OPEN_QUESTIONS.md#q-005--какие-прокси-и-как-ими-управлять)

### HTTPS-прокси без авторизации

7 ноября 2026 года реализован явный `auth_type: none`: запрос содержит только IP, порт и режим. Старые запросы без типа остаются `basic`, миграция `0015_proxy_auth_type` сохраняет старые версии и шифротексты. Для `none` хранится зашифрованная привязка с двумя `null` вместо реквизитов; отдельный ключ нужен в обоих режимах. Смешанный ввод отвергается, `credentials_configured` для `none` равен `false`. Заголовок `Proxy-Authorization` отсутствует. Подмена типа в БД, отсутствие ключа и отзыв блокируют подключение. `407` не включает Basic или прямой обход.

Прошли 12 тестов профилей с настоящими локальными TLS-сокетами и полный прогон 166 серверных тестов на PostgreSQL за 275,04 с. Проверка моделей не нашла расхождений с миграцией. Старый Basic, сроки хранения старых версий и ротация ключей сохранены.

В рабочей PostgreSQL `ergo_ms` применена `0015`, Django, Scout worker и Beat запущены штатными скриптами. Через открытый `103.62.50.130:443` с проверяемым TLS-именем `au-007.windscribe.com` завершён сбор Books to Scrape: одна HTML-страница дала 20 непустых названий и цен, 40 Evidence. Прямой сбор дал те же значения и количество. В первом полном сравнении предпросмотр через прокси занял 7,156 с, сбор 4,687 с; напрямую — 4,484 и 4,609 с, включая HTTP-опрос состояния. Это приёмка одной страницы, а не нагрузочный замер. Рабочий предел остаётся 200 страниц.

Запись профиля выполнялась через временный TLS-вход в настоящий Django WSGI с проверенным локальным сертификатом: ограничение HTTPS и сертификаты внешнего прокси/источника не отключались. Живой Celery отклонил loopback и облачные метаданные с `url_blocked`; чужой пользователь получил 404 для профиля. Read-only проверка 40 сообщений Scout реального брокера подтвердила UUID и номера попыток без IP прокси и контрольных реквизитов. Проверочный владелец, задания, профили и неиспользуемые снимки удалены отдельно от прежних данных.

На предварительных попытках открытые `87.249.132.97:9443` и `103.62.50.130:443` отдавали `407`, в том числе после успешной проверки подключения. Scout завершал такие попытки без данных и прямого обхода. Последующий успешный сбор не доказывает постоянной доступности узла. Автоматическая ротация и поддержка SOCKS5 не добавлялись; выбор поставщика для эксплуатации остаётся отдельным решением. Форма и выбор `basic` / `none` относятся к FE-001. ## Исправления серверного сбора и очистки

12 ноября 2026 года проверка предпросмотра стала обязательной для подтверждения и старта ручного плана. Неверные типы полей задания возвращают HTTP 400. История расписания определяет `superseded` по времени изменения настроек независимо от задержки Beat.

Основной обход повторяет загрузку стартового адреса после ошибки предпросмотра, учитывает общий снимок редиректа один раз и отбрасывает ответы после дедлайна. Загрузчик обрабатывает кириллические URL и оборванные ответы. Извлечение определяет кодировку по заголовку и объявлениям документа, принимает XHTML с XML-декларацией и сохраняет ссылки при ошибочном `base`.

Очистка повторно проверяет политику перед фиксацией удаления HTML, учитывает прерванные выгрузки и показывает защищённые результаты в перечне. Неисполнимый автоматический предпросмотр сохраняется один раз за дату UTC.

DNS при основном обходе использует тот же дедлайн, что подключение и чтение ответа. При истечении срока сбор перестаёт ждать DNS, а системный вызов завершает работу в фоне. Регрессионный тест проверяет, что заблокированный DNS не удерживает попытку и запоздалый результат не используется для подключения.

Полный прогон рабочей копии на изолированном PostgreSQL прошёл все 225 серверных тестов Scout, включая проверку заблокированного DNS. Проверка `makemigrations --check --dry-run scout` не обнаружила изменений схемы.
