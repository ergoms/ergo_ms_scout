## Исправления и границы 2A

- Ограничены все новые frontier-строки, включая skipped и redirect-алиасы. Загрузка, поиск ссылок и извлечение остаются самостоятельными Task.kind.
- При захвате fetch под блокировкой Run резервируется допустимый размер ответа; лимит проверяется для уже поставленных задач. Достижение времени и размера закрывает ожидающие загрузки и сохраняет частичный результат.
- Общая задержка проверяется между началами попыток загрузки, concurrency — по leased fetch. Retry не создаёт новую строку URL или отдельную fetch-задачу.
- Загрузчик принимает независимую проверку URL; допустимость redirect проверяется до следования. Значимые query, их порядок/повторы/кодирование и path params сохраняются; tracking удаляется только по политике плана.
- Завершение fetch во время pausing сохраняет работу для resume. Отмена отбрасывает поздние записи и закрывает frontier. Периодическая сверка восстанавливает frontier по Task/снимкам, не по пустоте брокера.
- Контрольный URL и лимиты доступны в UI/CLI и включены в неизменяемый план/hash. Нулевая глубина сохраняется. Предпросмотр не запускает обход. UI показывает границы и причину частичного итога на ru/en/fr.
- Бюджет времени начинается с основного старта. Дополнительное исправление байтового бюджета учитывает только снимки, включённые в основной frontier; контрольный preview вне обхода не расходует его. Повторно используемый снимок должен укладываться в основной лимит.
- Лимит байтов означает принятый распакованный HTML; это не лимит всего сетевого трафика повторов или заголовков. Текущая версия также не гарантирует единственный сетевой запрос к назначению двух одновременно выполняющихся redirect: уже leased запрос нельзя отозвать по ещё неизвестному alias.
- Новых моделей и миграций в этой проверке не добавлялось; используется существующий CrawlURL этапа 2A. Поиск, LLM, браузерное извлечение, граф блоков и очереди 2B не реализовывались.

В браузере показан частичный bytes-итог, затем скачаны JSON/CSV обхода: 4 строки с одинаковыми public_id/title и evidence. Материалы: `phase2a-crawl.json`, `phase2a-crawl.csv`, `phase2a-crawl-result.jpg`.

## Что сделал обход

Режим по умолчанию по-прежнему «только указанные страницы». «Обойти сайт» включается в плане и попадает в хеш подтверждения. Предпросмотр качает только семена, не весь сайт. После подтверждения загрузка, поиск ссылок и извлечение — разные задачи. Очередь адресов лежит в `CrawlURL` с уникальным ключом на запуск. Потолок по умолчанию: 50 страниц, глубина 2, 10 минут, 200 адресов в очереди, 2 одновременные загрузки. Потолок — не обещанное число страниц.

Команда `ergoms scout:collect` принимает `--crawl site`, `--allow-host`, `--visit-prefix`, `--extract-prefix`, `--depth`, `--max-pages` и по-прежнему только готовит предпросмотр. Сбор без подтверждения она не начинает.

## Проверки, которые прошли

На локальном HTTP-стенде внутри тестового процесса, теми же функциями задач, что вызывает воркер:

- Цикл `/a` → `/b` → `/a` и якорь `#frag` дали два адреса, две загрузки и две записи.
- Чужой хост и `.pdf` попали в очередь с причинами `host` и `document`, без загрузки.
- Каталог `/cat` не стал записью, когда записи берутся только с `/item/`. Ссылки `?page=2` и `?id=9` сохранились как разные адреса.
- Редирект `/go` → `/quiet` скачался один раз, цель помечена `redirect`.
- Один и тот же адрес с якорем не создал вторую задачу загрузки.
- Пауза оставила очередь, продолжение довело запуск до `completed`.
- Отменённый запуск не породил новую загрузку из позднего разбора ссылок.
- Незакрытая задача обхода не дала завершить запуск раньше времени.
- Просроченная аренда задачи обхода вернула её в `pending` и не завершила запуск.
- Ответ 503 на `/flaky` повторился без второго ручного старта и дошёл до предпросмотра.
- Чужой пользователь получил 404 на задание и запуск и 403 на выгрузку.
- Прежний сценарий одной страницы, включая отказ старта без подтверждения, остался зелёным в том же прогоне.

## Что не подтверждено живым процессом

Уже запущенные Beat и `start-worker --worker=all` в этом прогоне не исполняли новый код обхода. В журнале Beat нет задачи `scout-dispatch-pending`: процесс поднят раньше, чем расписание модуля стало ему известно. Повтор 503, пауза и потеря аренды проверены функциями задач в тестовом процессе (`SCOUT_TASK_RUNNER=inline`), не отдельным живым воркером Celery.

Два процесса воркера одновременно один и тот же адрес не запускались. Проверена повторная запись одного адреса в одном процессе: вторая задача загрузки не создаётся. Блокировка строки запуска в коде есть, гонка двух процессов на PostgreSQL отдельно не гонялась.

Браузерный проход «настройка → предпросмотр → пауза → выгрузка» в этом заходе не делался. Пароль учётки в `env/mcp.env` пустой, форма входа дальше не открывалась.

Выгрузка JSON/CSV обхода отдельным файлом не снималась. Путь выгрузки одной страницы в том же наборе тестов прошёл.

## Остановка обхода

Причина пишется в `stop_reason`: `max_pages`, `frontier`, `time`, `bytes`. Ссылка вне правил не считается ошибкой разбора: у неё `skip_reason` (`host`, `visit`, `depth`, `document`, `scheme`, `fragment`).
