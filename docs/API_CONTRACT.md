# SCOUT — граница FRONTEND и SYSTEM

Актуализировано 7 ноября 2026 года. Работающие операции и расширения описываются с явным статусом; клиентская интеграция проверяется отдельно от серверной реализации.

SYSTEM отвечает за соответствие описания серверу, FRONTEND — за проверку достаточности данных для интерфейса. Порядок изменений — в [TEAM_WORKFLOW.md](TEAM_WORKFLOW.md).

## Источник текущего поведения

- [urls.py](../api/urls.py) — пути операций внутри префикса `/api/scout/`.
- [views.py](../api/views.py) — методы, тела запросов и ответы.
- [tree_views.py](../api/tree_views.py) и [visual_tree.py](../api/services/visual_tree.py) — метаданные дерева, поиск, версии и курсоры API-004.
- [present.py](../api/present.py) — поля ответов.
- [constants.py](../api/services/constants.py) — состояния и текущие ограничения.
- [integrations.py](../api/integrations.py) и [permissions.py](../api/permissions.py) — ошибки и права.
- [endpoints.js](../client/js/endpoints.js) — относительные адреса клиента; префикс и авторизацию добавляет общий `apiClient`.

Внешние идентификаторы объектов — UUID в `public_id`. DOM-узлы имеют локальные `node_id` вида `n1`, связанные со снимком и его версией. Числовые ключи БД в клиентский контракт не входят. Операции требуют аутентификации и соответствующих прав; доступ ограничен владельцем согласно текущему серверному коду.

## Работающие операции

Все пути ниже относительны к `/api/scout/`:

- `GET health/` — состояние модуля; это не публичная анонимная проверка.
- Загрузка/чтение снимка и проверка правил — [API-002](#api-002--серверный-черновик-для-ux-001).
- `GET visual-snapshots/{public_id}/tree/` — корни или непосредственные дети, курсоры и окно вокруг узла.
- `GET visual-snapshots/{public_id}/tree/nodes/{node_id}/` — узел и цепочка родителей.
- `POST visual-snapshots/{public_id}/tree/search/` — буквальный поиск по всем разрешённым метаданным. [API-004](#api-004--dom-дерево-снимка).
- Политика хранения, закрепления, предварительный просмотр и исполнение очистки — [SCALE-001](#scale-001--сроки-хранения-и-очистка).
- `POST plan-suggestions/` — черновик плана по готовому снимку при включённом AI-001. [Формат запроса и ответа](#ai-001--черновик-плана-по-описанию)
- `GET jobs/` — объект с массивом `jobs`, сейчас не более 100 заданий.
- `POST jobs/` — создание задания; поля запроса: `title`, `seed_urls`, `fields`, `record`, `crawl`; ответ задания, HTTP 201.
- `GET jobs/{public_id}/` — задание и последняя версия плана.
- `PATCH jobs/{public_id}/` — новая версия настроек. Текущий обработчик ожидает адреса и поля плана; частичное изменение только заголовка не считать гарантированным сценарием.
- `POST jobs/{public_id}/explore/` — предварительная загрузка; ответ запуска, HTTP 202.
- `GET/POST/PATCH jobs/{public_id}/schedule/` — ежедневное расписание закреплённого плана. [Контракт расписания](#ext-002--ежедневное-расписание)
- `GET jobs/{public_id}/schedule/occurrences/` — история назначенных дней и пропусков.
- `GET runs/{public_id}/` — состояние запуска. Перед подтверждением полный ответ может содержать предпросмотр. Для опроса прогресса есть `?summary=1`.
- `POST runs/{public_id}/approve/` — подтверждение версии плана.
- `POST runs/{public_id}/start/` — начало основного сбора; HTTP 202.
- `POST runs/{public_id}/pause/` — запрос паузы; ответ запуска.
- `POST runs/{public_id}/resume/` — продолжение; HTTP 202.
- `POST runs/{public_id}/cancel/` — запрос отмены; ответ запуска.
- `GET runs/{public_id}/records/` — объект с массивом `records`. Параметры `limit` и `cursor` включают постраничную выдачу.
- `GET runs/{public_id}/compare/` — сравнение с более ранним запуском по SKU и выбранному полю. [EXT-002](#ext-002--api-сравнения-запусков)
- `POST runs/{public_id}/export/` с `kind: json` или `csv` — `download_url`, `filename`, `kind`. Подписанную ссылку формирует сервер; клиент её не вычисляет.

HTTP 202 означает принятие операции, а не завершение сбора. Для результата действия клиент читает состояние запуска. Подтверждение и старт — разные серверные операции, даже когда интерфейс объединяет их в одно действие.

## Основные ответы

Задание: `public_id`, `title`, `revision`. Версия может быть `null`; иначе содержит `public_id`, `revision_number`, `seed_urls`, `record`, `fields`, `limits`, `crawl`, `plan_hash`, `approved`. `record` может быть `null`. Поля версии определяются сервером, а не отдельным форматом для каждого способа настройки.

Запуск: `public_id`, `status`, `error_summary`, `job_public_id`, `plan_hash`, `crawl`, `approved`, `snapshot_count`, `record_count`, `stop_reason`, `frontier`, `journal`, `events`, `tasks`.

`frontier` содержит счётчики `queued`, `active`, `done`, `skipped`, `failed`. Каждая запись `tasks` содержит `public_id`, `kind`, `status`, `error_code`, `error_message`. Это состояния серверных задач; загрузку кнопки или несохранённую форму клиент ведёт отдельно.

`preview` присутствует не во всех ответах. В ожидании подтверждения он может содержать массив примеров с `source_url`, `values`, `evidence`; при ошибке предпросмотра — объект `error` с ошибкой Scout. Отсутствие поля, пустой массив и ошибка имеют разный смысл.

Запись результата по умолчанию содержит `public_id`, `values` и `evidence`. У значения поля есть `raw` и `normalized`. Evidence содержит `field_path`, `source_url`, `locator`, `raw_value`, `normalized_value`, `extractor_id`, `extractor_version`. Для цены, количества и даты можно запросить [режим DATA-001](#data-001--типизированные-значения-и-evidence).

## Порции результата и опрос прогресса

- Первый запрос страницы выглядит как `GET runs/{public_id}/records/?limit=50`. Сервер возвращает `records` и `next_cursor`. Передайте полученный курсор в следующем запросе вместе с `limit`. `next_cursor: null` означает конец списка на момент запроса.
- `limit` принимает целое число от 1 до 200. Запрос с одним `cursor` использует 50 строк. Курсор — `public_id` последней показанной записи этого запуска. Неверный `limit` или `cursor` даёт HTTP 400 с кодом `invalid_limit` или `invalid_cursor`.
- Строки идут по времени создания со стабильным порядком при одинаковом времени. `Evidence` входит в каждую строку. Запрос без `limit` и `cursor` возвращает весь массив в прежнем формате. Для завершённого результата все порции образуют тот же набор записей, что и полная выдача.
- `GET runs/{public_id}/?summary=1` возвращает идентификаторы, состояние, подтверждение плана, причину остановки и счётчики `snapshot_count`, `record_count` и `frontier`. Для задач, журнала и предпросмотра запрашивайте полный ответ.
- Экспорт доступен после завершения сбора, включая завершение с ошибками. JSON содержит записи и Evidence, CSV — идентификаторы и нормализованные значения. Сервер формирует файл порциями и передаёт его в Media API, затем возвращает подписанную ссылку.

## Состояния и ошибки

Состояния запуска: `exploring`, `awaiting_confirmation`, `running`, `pausing`, `paused`, `cancelling`, `cancelled`, `completed`, `completed_with_errors`, `failed`.

UI не подменяет ответ сервера оптимистическим завершением паузы, отмены или всего сбора. При смене задания запоздалый ответ прежнего запроса не должен заменять текущие данные. Точный набор доступных действий и причин частичного результата уточняется совместно с макетами.

Ошибки Scout возвращаются как `code` и `detail`. `approval_required`, `slot_busy`, `plan_changed`, `invalid_state` дают HTTP 409; ошибка `media` — 503; остальные ошибки Scout — 400. Аутентификация, права и отсутствие объекта могут давать стандартные ответы DRF с `detail`, без `code`; клиент должен их различать.

## Сетевая политика загрузки HTML

Прямой режим предпросмотра, сбора и визуальных снимков загружает публичные HTTP(S)-адреса через стандартные порты. На каждом редиректе Scout повторяет проверку назначения и соединяется с проверенным IP. В режиме обхода дополнительно проверяются разрешённые домены, а при основном сборе действуют фильтры переходов. Администратор может добавить точные пары IP и порта через `SCOUT_TRUSTED_FETCH_ENDPOINTS`, например `127.0.0.1:8765` или `[::1]:8765`. Исключение действует только для URL с указанным IP и портом. Для выбранного прокси применяется [SPEC-004](#spec-004--профили-прокси).

Предел ответа по умолчанию — 1 000 000 байт до и после распаковки. Таймаут сетевой операции по умолчанию — 20 секунд, число редиректов ограничено пятью. У задач предпросмотра и сбора до трёх попыток при сетевой ошибке или HTTP 429, 500, 502, 503, 504. Запрещённое назначение (`url_blocked`), выход редиректа за границы плана (`redirect_scope`) и превышение размера (`too_large`) считаются окончательными ошибками загрузки.

## SITEMAP-001 — XML-карта сайта

В `POST jobs/` и `PATCH jobs/{public_id}/` можно передать `crawl: {"mode": "site", "sitemap_url": "https://example.com/sitemap.xml"}` вместе с остальными полями плана. Адрес карты входит в версию и `plan_hash`, возвращается в `revision.crawl` задания и `crawl` запуска. Пустая строка или `null` означают обход без карты. Хост карты должен входить в `allowed_hosts` (по умолчанию — хосты `seed_urls`). Для CLI: `ergoms scout:collect --crawl site --sitemap-url https://example.com/sitemap.xml` с обычными параметрами страницы, полей и пользователя.

Предпросмотр по-прежнему требует хотя бы один HTML-адрес в `seed_urls`; он не загружает карту. После `approve/` и `start/` задачи `sitemap` читают `urlset` или `sitemapindex`, в том числе gzip. В [протоколе Sitemaps](https://www.sitemaps.org/protocol.html#sitemapIndex) индекс содержит абсолютные адреса дочерних карт того же сайта. Scout требует совпадение канонического имени хоста с корневой картой; более широкий `allowed_hosts` не разрешает сторонний хост для дочернего XML. Поддомены считаются другим хостом карты. Порт и фактический IP проверяются общей сетевой политикой на каждом соединении и редиректе, включая выбранный профиль прокси.

### Индекс, общий план и ограничения

Тело запроса и CLI не меняются: в `crawl.sitemap_url` передают адрес отдельной карты либо индекса. Новых маршрутов, обязательных полей плана и миграций нет. Старые планы `urlset` сохраняют прежние правила очереди и хеш; план без карты работает как раньше. Адрес индекса входит в подтверждённую версию; содержимое карт загружается заново при каждом основном сборе, включая запуск по расписанию. `lastmod` и `priority` не меняют состав или порядок сбора в этом этапе.

Один XML-документ — одна короткая задача Celery в общей очереди `scout`. XML-задачи одного запуска исполняются последовательно, состояние подготовки и промежуточные адреса сохраняются в `Task.payload` корневой задачи. Дочерний индекс поддерживается как ограниченное расширение Scout: глубина XML-ссылок от корня 0 до 3, максимум 20 уникальных адресов XML-документов, включая корень. Это ограничения Scout, а не обещание загрузить предельные размеры протокола.

Общий бюджет XML равен `min(5_000_000, crawl.max_total_bytes)` байтов. Каждая попытка заранее резервирует `min(limits.max_bytes, оставшийся XML-бюджет)`; успешный разбор возвращает неиспользованную часть резерва. Неудачная или потерянная попытка расходует резерв целиком. Так повторы не обходят общий предел. Gzip ограничивается и в упакованном, и в распакованном виде. HTML сохраняет собственный существующий бюджет `max_total_bytes`; XML не считается HTML-снимком или страницей. Общее время XML и HTML ограничено `crawl.max_seconds` от старта запуска.

В одном XML и суммарно по прочитанным `urlset` допускается не больше 50 000 записей URL. До открытия обхода сохраняется не больше `frontier_cap + 1` уникальных подходящих адресов из индекса: дополнительный адрес позволяет зафиксировать ограничение, а не заявить полный сбор. Фильтры `visit` и `extract_on` относятся к HTML-страницам, а не к путям XML-карт. Начальные страницы карт имеют HTML-глубину 0, независимо от глубины XML-индекса. Один общий `max_pages`, не больше 200, применяется ко всему запуску вместе с `seed_urls`, а не отдельно к каждой карте.

### Дубли, циклы и открытие обхода

Адреса карт нормализуются по схеме, имени хоста, стандартному порту и фрагменту. Query сохраняется без удаления параметров: он может различать карты или содержать подпись. Повтор одного адреса создаёт одну задачу. Если разные адреса редиректят в один уже разобранный XML, повторный запрос для обнаружения редиректа возможен, но содержимое не регистрируется второй раз. Ссылка на себя или предка, в том числе через редирект, даёт `sitemap_cycle`; дополнительного запроса к уже известному предку нет.

Для индекса действует барьер: основной HTML-обход открывается только после успешной подготовки всех дочерних XML. До этого нет frontier основного обхода и новых записей результата. Уже загруженные при предпросмотре контрольные снимки остаются. При успехе адреса карт и семян попадают в общую очередь с обычной нормализацией, фильтрами, устранением дублей и пределами плана. Ссылки из HTML затем обходятся по прежним правилам.

Сбой одной карты не разрешает молча начать обход по остальным. При окончательной сетевой ошибке, битом XML, DTD, недопустимом дочернем адресе, цикле или превышении лимита подготовка завершается ошибкой: остальные ожидающие XML-задачи отменяются, запуск получает `failed`, основной обход не начинается. Истечение общего времени использует существующий `stop_reason: "time"` и частичную полноту; это не успешная полная подготовка карт. При временной ошибке HTTP действуют прежние повторы и срок аренды.

### Состояние API и ошибки

В `GET runs/{public_id}/`, в том числе с `summary=1`, добавлен объект `sitemap` (до создания корневой задачи — `null`):

```json
{
  "maps_discovered": 4,
  "maps_processed": 4,
  "url_entries": 4,
  "xml_bytes_charged": 640,
  "ready": true,
  "max_maps": 20,
  "max_depth": 3,
  "max_xml_bytes": 5000000
}
```

`maps_discovered` считает уникальные адреса задач, `maps_processed` — уникальные успешно разобранные конечные адреса XML (поэтому алиасы могут дать меньше). `url_entries` включает повторы URL внутри карт; это не число записей результата. `xml_bytes_charged` включает консервативный расход неудачных попыток. `ready` означает открытие HTML-обхода после подготовки. Ошибки доступны через прежние `error_summary`, `tasks[].error_code` и `error_message`; поля прокси и XML не добавляются в общий ответ.

Коды: `sitemap_invalid` — некорректный XML, другой корень, DTD или неверный loc индекса; `sitemap_empty` — пустая карта/индекс; `sitemap_scope` — дочерняя карта другого хоста; `sitemap_cycle` — ссылка на предка; `sitemap_limit` — число карт, глубина или количество URL; `sitemap_budget` — исчерпан XML-бюджет. Также сохраняются ошибки загрузки `url_blocked`, `http_404`, `redirect_scope`, `too_large` и ошибки профиля прокси. Прежний `sitemap_index_unsupported` для нормального индекса больше не возвращается.

Пауза сохраняет промежуточные данные и дочерние задачи; продолжение не перечитывает успешно завершённые карты. Отмена и устаревшая попытка не открывают frontier. После падения worker Beat восстанавливает просроченную аренду и неопубликованные задачи; повторная доставка не регистрирует страницы и Evidence повторно. RSS и текстовые списки адресов остаются отдельными расширениями.

### Поиск карт через robots.txt

В `POST jobs/` и `PATCH jobs/{public_id}/` вместо явного адреса можно включить `crawl: {"mode":"site","sitemap_from_robots":true}`. Остальные поля плана остаются обычными. CLI: `ergoms scout:collect --crawl site --sitemap-from-robots --url https://example.com/catalog/ ...`. Флаг требует `mode: "site"` и не допускает одновременного непустого `sitemap_url`; неверный тип флага и конфликт дают HTTP 400 `invalid`. Поле включается в нормализованный план и хеш только при `true`: старые планы, отсутствие поля и явный `false` сохраняют прежние хеши. Миграция не требуется, новых маршрутов нет.

Scout берёт схему, хост и порт **первого** нормализованного `seed_urls`, заменяет путь на `/robots.txt`, удаляет query и фрагмент. Например, `https://example.com/catalog/?page=2` даёт `https://example.com/robots.txt`. Прочие семена сохраняются в общем обходе; автоматический поиск на каждом разрешённом хосте не выполняется. Предпросмотр проверяет HTML как раньше. `robots.txt` загружается только после подтверждения и старта, заново в каждом сборе, в том числе по расписанию.

Из UTF-8-текста, включая BOM и CRLF, читаются все строки `Sitemap:` независимо от группы `User-agent`, регистра директивы и комментариев после `#`. Значение требует абсолютный HTTP(S)-адрес до 2000 символов. Несколько объявлений допустимы по [протоколу Sitemaps](https://www.sitemaps.org/protocol.html#informing): каждое может вести на `urlset` или `sitemapindex`. Неправильная директива `Sitemap` делает подготовку ошибочной целиком. Неизвестные директивы не участвуют в поиске. Этот этап реализует обнаружение карт; применение `Allow`, `Disallow` и `Crawl-delay` к HTTP-обходу не добавляется.

Файл robots — одна задача `sitemap` с источником `robots`, найденные XML — отдельные обычные задачи карт. Все используют общую сетевую политику, закреплённую версию прокси, проверку фактического IP и каждого редиректа. XML и редиректы robots должны оставаться на том же каноническом хосте; это ограничение Scout сохраняется и для объявления сторонней карты. Публичный ввод не разрешает доступ к закрытой сети. Фильтры HTML `visit`/`extract_on` не отсекают `/robots.txt` и XML.

Размер robots до и после распаковки — не больше `min(512*1024, limits.max_bytes, оставшийся бюджет карт)` байтов. Его резерв и повторы расходуют **тот же** бюджет подготовки `min(5_000_000, crawl.max_total_bytes)`, отражённый в `xml_bytes_charged`; неудачная попытка расходует резерв целиком. До 20 XML-документов считаются без robots, начальные карты имеют XML-глубину 0, вложение — до 3. Общий срок включает robots, XML и HTML. Адреса всех карт и семян объединяются с защитой от дублей и прежним потолком **200 HTML-страниц на запуск**. Основной frontier открывается после успешного разбора всех карт.

Если robots недоступен, нет директив `Sitemap` или одна из карт повреждена, запуск завершается в `failed` до основного HTML-обхода. Автоматического перехода к другим способам обнаружения нет. Коды `http_404`, `http_503`, `network`, `too_large`, `url_blocked`, `redirect_scope` и ошибки прокси сохраняются; сетевые ошибки и временные HTTP-коды повторяются до трёх попыток. Дополнительно: `robots_no_sitemap` — нет адресов карт; `robots_invalid` — неверная кодировка, HTML/управляющие символы вместо текста или неверное значение `Sitemap`. Ошибки карт используют прежние `sitemap_invalid`, `sitemap_scope`, `sitemap_cycle`, `sitemap_limit`, `sitemap_budget`. В журнале указано, что не удалось прочитать: robots или карту. Предпросмотренные контрольные HTML-снимки при ошибке подготовки не удаляются.

В объект `sitemap` ответа запуска, включая `summary=1`, для этого режима добавлены `discovery: "robots"`, `robots_url`, `robots_processed` и `max_robots_bytes: 524288`. Счётчики `maps_discovered`/`maps_processed` относятся только к XML, `ready` означает открытие основного обхода. До создания корневой задачи объект равен `null`. Поле `robots_processed` становится `true` после атомарной регистрации найденных карт. Пауза, отмена, потеря публикации, срок аренды и повторная доставка используют прежний механизм карт; успешно завершённый robots при продолжении не перечитывается. Поле включения и показ ошибок в клиенте — отдельная интеграция FRONTEND.

## API-002 — серверный черновик для UX-001

Сервер поддерживает перечисленные операции. Клиент UX-001 использует их для загрузки, выбора элементов, проверки CSS и передачи принятых правил в общий план. Смена URL и выход из визуального режима прекращают опрос и делают запоздалые ответы неактуальными. HTTP 404 предлагает новую загрузку без удаления принятых правил.

- `POST visual-snapshots/` с `{"url":"https://example.com/catalog"}` — HTTP 202, `public_id` и `status: "loading"`. Снимок можно запросить до создания задания. Сервер загружает одну открытую HTML-страницу через очередь Scout. У загрузки предел 1 МБ и 30 запросов на пользователя в час (HTTP 429 при превышении).
- `GET visual-snapshots/{public_id}/` — HTTP 200, `public_id` и `status`. Пока снимок `loading`, клиент периодически запрашивает его состояние. Для `ready` сервер добавляет `final_url`, `html` и `tree_version`. Для `failed` сервер добавляет `error: {"code":"not_html","detail":"Ответ не является HTML"}`. Если подготовка не закончилась за две минуты, возвращается `load_timeout`.
- `POST visual-snapshots/{public_id}/check/` — HTTP 200 с проверкой CSS на этой версии снимка. Готовый селектор передаётся как `kind: "css"` и `selector`. Чтобы получить предложение по клику, вместо этих полей передаётся `node_id`. Для снимка, который ещё загружается или завершился ошибкой, сервер возвращает HTTP 409 с `code: "snapshot_not_ready"`.

Для чтения и проверки требуются аутентификация и `scout_configure`, для загрузки дополнительно требуется `scout_run`. UUID закреплён за одной загрузкой. Просроченный через час или чужой снимок даёт HTTP 404. Для снимка действует общая сетевая политика загрузки HTML. Пользователь может повторить загрузку новым запросом.

`html` — структурное представление без сторонних стилей, скриптов, активных ссылок и загрузки ресурсов. Клиент должен отображать его в изолированном `iframe` с отключёнными скриптами. Атрибут `data-scout-node` связывает отображённые элементы с исходным снимком и используется только в его пределах.

Пример проверки поля после клика:

```json
{
  "record": {"kind": "css", "selector": "article.product"},
  "field": {"name": "price", "scope": "record", "many": false, "node_id": "n24"}
}
```

Чтобы предложить правило карточки отдельно, передайте `{"record":{"node_id":"n12"},"field":null}`. Для поля на всю страницу передайте `record: null` и `scope: "page"`. Если предлагаемый селектор не найден, сервер возвращает HTTP 400 с `selector_not_suggested`. Некорректные селекторы, неизвестный элемент или выбор за пределами карточки также дают HTTP 400 с `code` и `detail`.

Ответ содержит `record` и `field` в формате обычного плана либо `null`, `row_count` с общим числом строк и `rows` с примерами (до 20). Строка карточки содержит `node_id` для подсветки либо `null`, когда видимого элемента нет. При проверке поля в строку добавляются `match_count`, `match_node_ids` (до 20 видимых элементов) и `value` с `raw` и `normalized`. Ноль совпадений даёт `value: null`. При `many: false` возвращается первое значение, при `many: true` применяется формат нескольких значений существующего извлекателя. Проверка на снимке предшествует сохранению плана и обычному предпросмотру.

## API-004 — DOM-дерево снимка

**Серверный контракт v1 реализован и проверен.** Ниже — форматы для интеграции UX-004/FE-005; условные UUID/версии/курсоры примеров не являются рабочими токенами. Владение, срок снимка и проверка правил остаются за API-002. Полный прогон — 178 серверных тестов; результаты живых HTTP/Celery и перезапуска — в [статусе реализации](IMPLEMENTATION_STATUS.md#api-004--dom-дерево-снимка). Полный префикс новых путей — `/api/scout/`; `S` в примерах обозначает UUID снимка. Значения `tree_version` и курсоров в примерах условные; рабочие значения создаёт сервер.

### Область дерева и формат узла

Дерево описывает **исходные элементы, представленные в безопасном снимке**, а не весь сырой DOM сайта. Используется та же карта `VisualDocument.nodes`/`ids`, что в `data-scout-node` и `/check/`. Удалённые ветви `head`, `script`, `style`, `iframe`, `object`, SVG и остальные исключения текущего редактора не становятся узлами API-004. Синтетические оболочки `html`/`body` iframe не получают новых ID: корней может быть несколько, у них `parent_id: null`.

Номера не переназначаются при поиске, фильтрации или загрузке ветви. Обход — в порядке документа, сначала узел, затем его дети. `node_id` имеет формат `n[1-9][0-9]{0,4}` (диапазон реально выданных ID ограничен размером снимка). Идентификатор вида `n1` имеет смысл только вместе с UUID снимка и его `tree_version`, не является глобальным идентификатором и не переносится в новый снимок.

Один `Node` имеет неизменный набор полей:

- `node_id: string` — ID API-002; `parent_id: string|null` — ближайший представленный родитель.
- `child_index: integer` — позиция с нуля среди непосредственных представленных детей родителя; для корней — среди корней. Это не CSS `nth-child` исходного документа.
- `depth: integer` — глубина с нуля от корня; `children_count: integer` — число непосредственных представленных детей во всём дереве, не только в текущей порции.
- `tag: string|null` — исходное имя тега в нижнем регистре: ASCII `[a-z][a-z0-9:-]{0,63}`. Если имя не укладывается в разрешённый формат, возвращается `null` и `metadata_limited: true`.
- `rendered_tag: string` — фактический безопасный тег iframe. Например, для изображения `tag: "img"`, `rendered_tag: "span"`; это один и тот же `node_id`.
- `element_id: string|null` и `classes: string[]` — ограниченные исходные метки. Для ID разрешён ASCII `[A-Za-z_][A-Za-z0-9_-]{0,127}`, для одного класса — `[A-Za-z_][A-Za-z0-9_-]{0,63}`. Классы уникальны, не более 8, в исходном порядке. Нестандартные/слишком длинные значения пропускаются целиком, не обрезаются до другого CSS-имени; при пропуске ставится `metadata_limited: true`. Если ID отсутствует или скрыт, поле равно `null`; если классов нет — `[]`.
- `text_preview: string` — до 120 Unicode-символов нормализованного текста **безопасного представления** этого узла, включая показанных потомков и подпись изображения. Пробелы схлопнуты, по краям удалены; пустой текст — `""`. Исключённые скрипты/ветви и исходные значения атрибутов не читаются в текст. При обрезке ставится `metadata_limited: true`.
- `metadata_limited: boolean` — хотя бы одна из перечисленных меток скрыта/ограничена. Это ограничение сведений об узле, а не потеря его детей или ошибка извлечения поля.

Метки предназначены для отображения и поиска. Они не вставляются как HTML или классы оболочки и не используются для самостоятельного построения рабочего CSS. По `node_id` API-002 проверяет **исходный** элемент; ограничения меток не запрещают выбор, но `/check/` может вернуть прежний `selector_not_suggested`. API-004 не обещает поддержку любого CSS/атрибута.

### Версия представления и совместимость API-002

`tree_version` — непрозрачная строка вида `dom-v1:<64 строчных hex>`, вычисленная из UUID/байтов/кодировки снимка и версии карты узлов/метаданных. Одинаковый неизменённый снимок при том же алгоритме даёт одинаковые узлы и версию после перезапуска. Изменение алгоритма, способное поменять карту или метки, меняет версию. Это проверка согласованности, не замена авторизации.

`GET visual-snapshots/S/` в состоянии `ready` **дополнительно** возвращает `tree_version`, соответствующий выданному `html`. Старые `public_id`, `status`, `final_url`, `html`, ответы `loading`/`failed`, TTL и правила доступа сохраняются. Текущий клиент читает известные поля и не обязан использовать добавление. В `POST visual-snapshots/S/check/` поддерживается **необязательное** верхнее поле `tree_version`: если передано, сервер сверяет его до проверки правила, при несовпадении отвечает HTTP 409 `tree_version_changed`. Старые запросы без поля продолжают работать и возвращать прежний формат. Правила, `match_count`, `rows` и предел выборки 20 не меняются. Расчёт версии не применяет новые пределы глубины/метаданных к старому GET или `/check/`: эти ограничения относятся только к API-004. Снимок API-002 не становится `failed` из-за отказа дерева.

Новый клиент берёт версию вместе с HTML и передаёт её во все операции дерева и проверки выбранного узла. Только первый запрос корней без `parent_id`, `cursor` и `around_node_id` может не иметь версии; остальные запросы требуют её. При HTTP 409 клиент сбрасывает старое дерево/выбор/проверку, получает заново HTML и его версию, сохраняя принятые правила как черновик для перепроверки. Если сервер ещё не реализует API-004, используется базовый UX-001 без имитации исходного дерева.

### Получение корней и ветвей

`GET visual-snapshots/S/tree/?limit=50&tree_version=<V>` — HTTP 200 с корнями. Без `parent_id` запрашивается виртуальный корень, отдельного узла `n0` нет. Ответ корней дополнительно содержит `scope: "selectable_snapshot_nodes"`, общее `node_count` и максимальную глубину всего представления. Число корней — `total_count`. Для снимка без представленных элементов ответ успешен: `node_count: 0`, `max_depth: null`, `total_count: 0`, `items: []`, курсоры `null`; текстовые узлы не получают самостоятельные ID.

```json
  "max_depth": 3,
  "parent_id": null,
  "total_count": 1,
  "items": [

      "node_id": "n1",
      "parent_id": null,

      "depth": 0,
      "tag": "main",
      "rendered_tag": "main",

      "classes": [
        "catalog"
      ],
      "text_preview": "Блокнот 1250,00 ₽ Обложка блокнота Карандаш",
      "children_count": 2,

```

`GET visual-snapshots/S/tree/?parent_id=n1&tree_version=<V>&limit=1` — только непосредственные дети `n1`, в исходном порядке. Ни в одном `Node` не возвращается вложенный массив `children`; связи задают `parent_id` и `children_count`.

```json
{
  "snapshot_public_id": "10000000-0000-4000-8000-000000000004",
  "tree_version": "dom-v1:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "parent_id": "n1",
  "total_count": 2,
  "items": [
    {
      "node_id": "n2",
      "parent_id": "n1",
      "child_index": 0,
      "depth": 1,
      "tag": "article",
      "rendered_tag": "article",
      "element_id": "sku-001",
      "classes": [
        "product",

      "metadata_limited": false
    }
  ],

  "next_cursor": "opaque-signed-cursor"

```

Общие параметры: `limit` — десятичное целое 1–100, по умолчанию 50; `cursor` — непрозрачный токен следующей/предыдущей порции. Пустой `parent_id`, повторённые/неизвестные параметры, дробь, отрицательное или превышающее предел число дают HTTP 400 `invalid_query`, а не молчаливую коррекцию. `total_count` — полное число детей выбранного родителя, `items` — текущая порция. `next_cursor`/`previous_cursor` равны `null` на соответствующем конце, не пустой строке. Для листа ответ успешен: `total_count: 0`, `items: []`, оба курсора `null`.

Чтобы открыть ветвь вокруг найденного узла, доступен `around_node_id`: `GET visual-snapshots/S/tree/?parent_id=n2&around_node_id=n5&tree_version=<V>&limit=50`. Узел должен быть непосредственным ребёнком запрошенного родителя; для корня `parent_id` опускается. Начало окна — `(child_index // limit) * limit`, окно содержит выбранный узел; курсоры позволяют идти в обе стороны. `around_node_id` нельзя совмещать с `cursor`; при переходе по курсору его убирают. Несуществующий узел даёт 404, неверная связь с родителем — 400 `node_not_child`. Не нужно последовательно читать все предыдущие страницы соседей ради подсветки.

### Поиск по всему доступному дереву

`POST visual-snapshots/S/tree/search/` — операция чтения без создания заданий и изменения снимка. JSON-тело передаёт поисковый текст, чтобы он не попадал в URL и обычный журнал путей:

```json
{
  "tree_version": "dom-v1:aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
  "q": "price",
  "tag": "span",
  "limit": 20
}
```

Поля: обязательные `tree_version` и строка `q`; необязательные `tag`, `limit` (по умолчанию 20, диапазон 1–100) и `cursor`. Остальные поля запрещены. `limit` должен быть именно целым JSON-числом, не строкой и не boolean; `cursor` — строка-токен. Для первой страницы `cursor` опускается, явный `null`/пустая строка запрещены. `q` нормализуется NFC, пробелы схлопываются/обрезаются, длина после нормализации 2–100 символов; нестроковое/пустое/слишком длинное значение — 400 `invalid_query`, `path: "/q"`. `tag` — необязательное точное имя исходного тега в допустимом формате, приводится к нижнему регистру; явный `null`/пустая строка запрещены. Чтобы убрать фильтр, поле опускают.

Поиск — буквальное вхождение нормализованной `casefold`-строки в **одно** из доступных значений `tag`, `element_id`, отдельный класс или `text_preview`; поля не склеиваются для совпадения. Каждое индексируемое значение нормализуется NFC/пробелами/`casefold` так же, как запрос; отображаемый исходный текст от этого не меняется. Пробелы в `q` не задают список условий. Поиск проходит все представленные узлы, включая ещё не раскрытые/не загруженные клиентом, и учитывает фильтр тега. Это не CSS, XPath, регулярное выражение, полнотекстовый поиск сырого HTML или поиск по другим страницам. Скрытые/обрезанные части меток не индексируются: граница поиска честно совпадает с показанными полями.

Результаты идут в порядке документа, без ранжирования. `total_count` — точное число подходящих узлов во всём разрешённом дереве, не число карточек и не число полей API-002. Пустой результат — HTTP 200, `total_count: 0`, `items: []`, курсоры `null`. Один и тот же текст может найти контейнер и его потомков; это не дубли товаров.

### Курсоры и лимиты v1

Курсор подписан сервером и связан с владельцем, UUID снимка, версией, видом операции, родителем либо хешем нормализованного поиска/фильтра, размером порции и позицией в документе. Текст `q` не записывается внутрь курсора. Курсор живёт не более 15 минут и никогда не продлевает часовой срок снимка; владение/TTL снимка проверяются на каждой странице до разбора курсора. Токен не даёт доступа без аутентификации. Длина — не более 2048 ASCII-символов. Для обычной пагинации параметры, кроме `cursor`, сохраняются; изменённые параметры требуют начать без курсора.

Стартовые пределы:

- Исходный HTML — прежний 1 000 000 байт, представленные элементы — прежние 10 000. Глубина API-004 — максимум 64 (корень имеет глубину 0), превышение запрещает **только дерево**, не меняет уже выданный `ready`/HTML и доступность старого API-002.
- Порция ветви/поиска — максимум 100 узлов; цепочка — максимум 64 предка. JSON каждого успешного ответа — максимум 256 КиБ в UTF-8 без сжатия; JSON-тело поиска — максимум 4 КиБ. Пределы полной структуры действуют для всех операций API-004: чтение отдельной ветви/узла не обходит ограничение глубины или количества. Разрешённые строки ограничены выше, максимальная допустимая порция должна помещаться в бюджет. Нельзя молча уменьшать порцию, пропускать узлы или показывать частичное дерево как полное: непредставимый объём даёт 422 `tree_too_large`.
- Общий лимит чтения корней/ветвей/узла — 240 запросов в минуту на пользователя (`scout_dom_read`), поиска — отдельно 60 в минуту (`scout_dom_search`), в дополнение к общим лимитам API. Превышение — 429 `throttled`, заголовок `Retry-After`. Поиск запускается явным действием или с задержкой ввода, не на каждое наведение.
- Чтение дерева не создаёт `Job`, `Run`, задач Celery, новых снимков, HTTP-запросов к источнику или вызовов ИИ. Рабочий предел сбора остаётся **200 страниц**. API-004 читает уже сохранённые байты; загрузка дерева/поиск не обновляют срок снимка.

Индекс/метаданные можно повторно использовать только с ключом владельца/UUID/версии и не дольше срока снимка. Построение должно иметь ограниченный обход без повторного полного чтения всех потомков каждого узла; новые службы хранения для этого контракта не требуются. Целевое время отклика не задавалось: разовые замеры рабочего каталога в статусе реализации не являются гарантией скорости для любого HTML.

### Ошибки и безопасность

Все операции требуют аутентификацию и `scout_configure`; `scout_run` повторно для чтения не требуется. Даже администратор не читает чужой снимок через эти операции: действует владелец API-002. Для дерева, поиска, узла и курсора одинаковый порядок проверок: права → владелец/срок снимка → готовность → параметры/версия → узлы/страница.

JSON ошибки содержит `code`, безопасный `detail` и необязательный `path` для поля ввода. Например:

```json
{
  "code": "tree_version_changed",
  "detail": "Представление снимка изменилось. Загрузите его заново."
}
```

- 401 `authentication_failed` — отсутствует/недействительна аутентификация; 403 `permission_denied` — нет разрешения настройки. Эти коды относятся к новым операциям; формат ошибок аутентификации API-002 не меняется.
- 404 `snapshot_not_found` — отсутствующий, чужой или просроченный снимок, одинаковый безопасный ответ; текущие 404 старого API-002 не меняются. 404 `node_not_found` — после проверки своего снимка запрошенный узел в нём отсутствует.
- 409 `snapshot_not_ready` — снимок ещё загружается или завершён ошибкой; состояние и исходную безопасную ошибку клиент читает существующим `GET visual-snapshots/S/`. 409 `tree_version_changed` — версия запроса или подписанного курсора устарела; получить заново HTML/версию, повторить выбор/проверку.
- 400 `invalid_query` — отсутствующая обязательная версия, неверные поля/типы/пределы, повторённые/лишние параметры или некорректный формат `node_id`/версии. 400 `node_not_child` — неправильный родитель для `around_node_id`. 400 `invalid_cursor` — повреждение подписи, чужая операция/снимок/владелец либо несовпадающие параметры. 400 `cursor_expired` — истёк курсор при ещё доступном снимке: начать чтение без него.
- 415 `unsupported_media_type` — поиск прислан не как JSON; неразбираемый JSON даёт 400 `invalid_query`, `path: "/"`. 413 `request_too_large` — тело поиска больше 4 КиБ; 422 `tree_too_large` — больше допустимых узлов/объёма; 422 `tree_depth_exceeded` — глубина больше 64. Усечения структуры нет, доступен прежний визуальный/ручной режим. Если сам снимок ранее отклонён API-002 как `too_large`, дерево возвращает `snapshot_not_ready`, не маскирует его готовым.
- 429 `throttled` — частота; 503 `storage_unavailable` — временно недоступно безопасное чтение/блокировка хранилища. Неожиданная ошибка — 500 `internal_error` без traceback и текста исходного HTML.

Возвращаются только перечисленные метаданные. Не возвращаются значения `href`, `src`, `style`, `data-*`, обработчиков событий/форм и адреса с параметрами из этих атрибутов, произвольный дамп или содержимое исключённых скриптов; подписи изображения берутся из уже безопасного представления. Подписи могут содержать недоверенный текст сайта: выводить текстовыми узлами, без `innerHTML`/`v-html`. DOM-дерево не восстанавливает удалённые ресурсы и не ослабляет `sandbox="allow-same-origin"` без `allow-scripts` либо CSP `default-src 'none'` снимка.

Режим прокси, ключи, реквизиты, содержимое HTML, поисковый текст, полные курсоры и текстовые метки не включаются в журнал/трассировку операций дерева. В аудите достаточно владельца/UUID, вида операции, количества, длительности и `request_id`; секреты не участвуют в JSON-ошибках или курсорах. Все ответы, включая ошибки, имеют `Cache-Control: no-store`. В клиентском постоянном хранилище DOM и ответы поиска не сохраняются; данные текущей сессии очищаются при смене снимка/выходе.

### Контрольный каталог и приёмка

Примеры используют локальный каталог ниже; внешние пути в атрибутах не загружаются редактором. Карта действующего API-002: `n1 main`; `n2 article`, `n3 h3`, `n4 a`, `n5 span.price`, `n6 img`; `n7 article`, `n8 h3`, `n9 a`, `n10 span.price`. Всего 10 узлов, один корень, максимальная глубина 3. `n6` показан как `span`, без смены ID. У второго товара цена пустая, но сам `span` существует; это не ноль совпадений.

```html
<!doctype html><html><head><meta charset="utf-8"><script>window.demo = "excluded"</script></head><body>
<main id="catalog" class="catalog">
 <article id="sku-001" class="product featured">
  <h3><a href="/one?token=demo">Блокнот</a></h3>
  <span class="price">1250,00 ₽</span>
  <img src="/cover.jpg" alt="Обложка блокнота">
 </article>
 <article class="product"><h3><a href="/two">Карандаш</a></h3><span class="price"></span></article>
</main></body></html>
```

Покрытие серверной проверки (тесты и живой сценарий):

1. Корни, дочерние страницы, пустой лист, путь/окно для узла в конце длинного списка и отсутствие пропусков/повторов при курсорах.
2. Узлы/ID/порядок совпадают с `data-scout-node` API-002, включая заменённый `img`; выбор карточки `n2` даёт две строки, поле `n5` — цену первого товара и существующее пустое значение второго.
3. Поиск `q: price`, `tag: span` даёт `n5` и `n10`, даже если в клиенте раскрыта только первая ветвь. Поиск буквальный, учтены Unicode/пробелы, пустой результат и запрещённый/слишком длинный ввод; скрытые атрибуты не находятся.
4. Подмена/истечение/перенос курсора, новая версия, чужой/просроченный снимок, неподготовленный снимок, неправильный родитель, запрос чужого `node_id` не раскрывают данные и дают указанные ошибки.
5. Ограничения 100/10 000/64, байтов и частоты проверены на пределе и за пределом; глубокий/объёмный отказ дерева не ломает старый API-002. Метки с HTML/опасными атрибутами и длинными CSS-именами безопасны и честно ограничены.
6. Новые операции не создают загрузок/задач/запусков, не трогают TTL; прежние JSON API-002 без новых полей продолжают работать. Версия/узлы воспроизводимы после перезапуска, секреты/поисковые данные отсутствуют в логах.

Эти случаи покрыты серверным набором и указанной живой приёмкой. Полная клиентская приёмка нового инспектора остаётся FE-005/FE-004. Единственная серверная задача — [API-004](../BACKLOG.md#api-004--безопасные-данные-дерева-для-визуального-инспектора); клиентский сценарий — UX-004/FE-005.

### Карточки каталога

Структура `article` взята со страницы `/full/items/1` из тестового каталога. [Страница приёмки DATA-001](../api/tests/fixtures/data001_catalog.html) содержит три карточки. Селектор карточки — `article`, селекторы полей — `.price`, `.quantity`, `.available-on`.

```html
<article>
  <h2>1-1</h2><span class="price">1&#8239;234,50 ₽</span>
  <span class="quantity">0</span><span class="available-on">06.11.2026</span>
</article>
<article>
  <h2>1-2</h2><span class="price"> </span>
  <span class="available-on">31.02.2026</span>
</article>
<article>
  <h2>1-3</h2><span class="price">по запросу</span>
  <span class="quantity">2,5</span><span class="available-on"></span>
</article>
```

### Хранение и преобразование

В подтверждаемом плане у скалярного поля появляется необязательная настройка `conversion`. Она хранится в версии плана, участвует в `plan_hash` и применяется одинаково в предпросмотре и сборе. Настройка разрешена для `many: false`, где сохраняется выбор первого совпадения. Поле без `conversion` использует текущий строковый формат.

```json
[
  {"name":"price","kind":"css","selector":".price","scope":"record","many":false,"conversion":{"type":"money","currency":"RUB","decimal_separator":","}},
  {"name":"quantity","kind":"css","selector":".quantity","scope":"record","many":false,"conversion":{"type":"integer"}},
  {"name":"available_on","kind":"css","selector":".available-on","scope":"record","many":false,"conversion":{"type":"date","format":"DD.MM.YYYY"}}
]
```

`Record.values` хранит `raw`, `normalized` и для поля с `conversion` объект `typed`. `raw` сохраняет извлечённый текст в пределах текущего лимита поля. `normalized` сохраняет его текстовую нормализацию. `typed` хранит результат преобразования, вычисленный один раз по подтверждённому правилу.

- **Цена (`money`).** `1 234,50 ₽` хранится как `{"amount":"1234.50","currency":"RUB"}`. Сумму разбираем как точное неотрицательное десятичное значение и сериализуем строкой. Для первого профиля RUB допускаем до двух дробных знаков и приводим результат к двум знакам без округления. Вход принимает корректные группы тысяч из пробелов, включая неразрывные, и заданный в правиле десятичный разделитель. Валюту задаёт правило. В профиле RUB суффикс `₽` или `RUB` допустим, явное несовпадение валюты даёт `currency_mismatch`. Текст `по запросу` даёт `invalid_decimal`.
- **Количество (`integer`).** `0` хранится числом JSON `0`. Первый профиль принимает целые числа от `0` до `2147483647`. Дробь `2,5` даёт `invalid_integer`. Целое за пределами диапазона даёт `value_out_of_range`.
- **Дата (`date`).** `06.11.2026` разбирается по заданному формату и хранится календарной датой `"2026-11-06"` без времени и часового пояса. Формат проверяется строго. Несуществующий день `31.02.2026` даёт `invalid_date`.

Для планов без профиля идентичности ключ повтора записи вычисляется из прежнего строкового представления и позиции карточки. Типизированное представление привязано к версиям схемы и правил. Идентичность товара между страницами и запусками описана в [SPEC-001](#spec-001--идентичность-товара).

### Состояния поля

- `ok` — значение преобразовано, `value` заполнено, `error: null`. Ноль относится к этому состоянию.
- `missing` — селектор вернул ноль совпадений. `raw` и `normalized` равны `""`, `value` и `error` равны `null`.
- `empty` — совпадение есть, извлечённый текст пуст или состоит из пробелов. `raw` сохраняет этот текст, `normalized` равно `""`, `value` и `error` равны `null`.
- `invalid` — текст есть, но преобразование завершилось ошибкой. `raw` и `normalized` сохраняются, `value: null`, `error` содержит машинный `code`. Если исходник пришлось обрезать, используется `value_truncated` до попытки преобразования.

Состояние определяется по совпадениям селектора и исходному тексту до нормализации. В XPath скалярный результат `""` считается совпадением с пустым значением, а пустой набор узлов даёт `missing`. Ошибка синтаксиса селектора относится к проверке правила. Строка с `invalid` сохраняется и выгружается, состояние запуска определяется исполнением задач.

### JSON и Evidence

Для типизированного результата используем `GET runs/{public_id}/records/?limit=50&value_format=typed_v1`. Полный ответ `GET runs/{public_id}/?value_format=typed_v1` использует тот же формат для `values` и `evidence` в `preview`. Для экспорта в `POST runs/{public_id}/export/` передаём `{"kind":"json","value_format":"typed_v1"}` или `{"kind":"csv","value_format":"typed_v1"}`. JSON-экспорт содержит массив записей, каждая запись совпадает по форме с элементом `records` этого режима. Неизвестный `value_format` даёт HTTP 400 с кодом `invalid_value_format`. Запросы по умолчанию используют строковый формат. Для исторических строк и полей без `conversion` выдаётся строковое представление `raw` и `normalized`.

Фрагмент `values` для карточки `1-1`.

```json
{
  "price": {"raw":"1\u202f234,50 ₽","normalized":"1 234,50 ₽","typed":{"type":"money","status":"ok","value":{"amount":"1234.50","currency":"RUB"},"error":null}},
  "quantity": {"raw":"0","normalized":"0","typed":{"type":"integer","status":"ok","value":0,"error":null}},
  "available_on": {"raw":"06.11.2026","normalized":"06.11.2026","typed":{"type":"date","status":"ok","value":"2026-11-06","error":null}}
}
```

Evidence в `typed_v1` связывает фактическое совпадение с URL, UUID снимка, версией правил и локатором. `raw_value` и `normalized_value` содержат текст с сайта, а `typed` лежит в `values`. Для `empty` и `invalid` Evidence сохраняется. Для `missing` причину показывает статус поля, поскольку совпадения для Evidence нет. При выдаче сохранённых записей UUID снимка и версии правил берутся из связей `Evidence.snapshot` и `Record.rules_revision`. В предпросмотре их дают текущий снимок и версия правил запуска.

Запись карточки `1-2` с пустой ценой, отсутствующим количеством и некорректной датой.

```json
{
  "public_id": "10000000-0000-4000-8000-000000000002",
  "values": {
    "price": {"raw":" ","normalized":"","typed":{"type":"money","status":"empty","value":null,"error":null}},
    "quantity": {"raw":"","normalized":"","typed":{"type":"integer","status":"missing","value":null,"error":null}},
```

### CSV

## SPEC-004 — профили прокси

Реализовано в серверном API. Выбор прокси относится к сетевому выходу загрузчика и применяется к предпросмотру, основному сбору и визуальному снимку, если при его создании явно выбрана версия профиля. Прямой режим описан в разделе [сетевой политики HTML](#сетевая-политика-загрузки-html).

### Ввод и выбор профиля

Владелец создаёт профиль через API, а в задании выбирает «Прямое подключение» или один профиль. Будущая форма FE-001 выбирает тип авторизации и показывает соответствующие поля.

- **Тип авторизации** — `auth_type: "basic"` или `"none"`. Пропущенное поле означает `basic` для совместимости со старым клиентом. Для `basic` обязательны оба реквизита. Для `none` поля `username` и `password` должны отсутствовать: пустые строки, `null`, один реквизит и смешанный ввод отклоняются. Переход между режимами создаёт новую версию через полный `PATCH`.

- **IP** — один IPv4 или IPv6 в канонической форме. Поле принимает буквальный IP без схемы, пути, скобок и номера порта. Список допустимых публичных пар IP и порта задаёт администратор развёртывания.
- **Порт** — целое число от 1 до 65535. Ввод проверяется вместе с IP по списку разрешённых пар.
- **Логин** — 1–128 печатных символов ASCII без пробелов и `:`. Это ограничение первой версии с Basic-аутентификацией.
- **Пароль** — 1–256 печатных символов ASCII, включая пробелы. Значение передаётся без обрезки и автоподстановок, поле маскируется. Логин и пароль записываются вместе при создании или замене реквизитов.

`POST proxy-profiles/` принимает JSON по HTTPS. В примере использован демонстрационный IP.

```json
{
  "ip": "192.0.2.10",
  "port": 8443,
  "username": "catalog-reader",
  "password": "example-only"
}
```

HTTPS-прокси без авторизации создаётся тем же запросом; IP здесь демонстрационный:

```json
{"ip": "192.0.2.10", "port": 8443, "auth_type": "none"}
```

`GET proxy-profiles/` возвращает до 100 профилей владельца. `GET proxy-profiles/{public_id}/` отдаёт метаданные профиля. После создания или `PATCH` с полным набором полей ответ содержит `public_id`, `revision_public_id`, IP, порт, `auth_type` и `credentials_configured`. Последнее поле равно `false` для `none`, даже при наличии зашифрованной привязки; это признак наличия реквизитов, а не доступности прокси. Логин и пароль доступны только на запись. `DELETE` отзывает профиль. При `PATCH` создаётся новая версия. В `POST jobs/`, `PATCH jobs/{public_id}/` и `POST visual-snapshots/` версию указывают как `proxy_profile_revision_public_id`. Явный `null` выбирает прямое подключение. При редактировании задания пропущенное поле сохраняет прежний выбор. В подтверждаемый план и его хеш входит UUID версии. Визуальный снимок фиксирует версию при постановке загрузки. Сообщение воркеру содержит UUID задачи или снимка. Воркер извлекает ссылку на версию из БД.

`POST proxy-profiles/{public_id}/check/` требует прав настройки и запуска, проверяет владельца и обращается к HTTPS-адресу `SCOUT_PROXY_CHECK_URL`. Страница проверки должна возвращать HTML с кодом 2xx, допускаются перенаправления в пределах того же имени. Пользователь получает `ready` или `failed` с безопасным кодом причины. Лимит проверки — 10 запросов в час на пользователя, бюджет одного запроса — 5 секунд. Используется тот же транспорт, что и при сборе.

### Транспорт и границы сети

Профиль поддерживает HTTPS-прокси с Basic-аутентификацией или без авторизации и `CONNECT` к HTTPS-источникам на порту 443. Защищённое соединение требуется уже между Scout и прокси. Прокси, который принимает обычный HTTP и лишь туннелирует HTTPS сайта, в этот профиль не входит. TLS-имя прокси берётся из административного списка для конкретной пары IP и порта. Соединение открывается к этому IP, сертификат проверяется по заданному имени или IP. [RFC 7617, безопасность Basic](https://www.rfc-editor.org/rfc/rfc7617.html#section-4) · [RFC 9110, CONNECT](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.6)

Проверки выполняются отдельно для адреса прокси и для назначения каждого туннеля. Для назначения сервер проверяет URL и ограничения плана, разрешает DNS и выбирает проверенный публичный IP. В `CONNECT` передаётся этот IP и порт 443. Внутри туннеля Scout проверяет сертификат источника и использует исходное имя сайта для TLS и `Host`. Каждый редирект повторяет проверки. Для IP, порта и TLS-имени прокси используются только одобренные настройки. Исключения `SCOUT_TRUSTED_FETCH_ENDPOINTS` для прямого загрузчика на этот режим не распространяются. [OWASP, защита от SSRF](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)

Локальные, частные, link-local и специальные IP, включая адреса облачных метаданных и IPv4 в IPv6, блокируются в обоих местах проверки. В режиме `none` заголовок `Proxy-Authorization` отсутствует. В режиме `basic` он отправляется только в запросе к прокси внутри защищённого соединения. Запрос к источнику использует отдельный набор заголовков. Настройки сетевого выхода API, Media API и брокера независимы от профиля Scout. Поставщик прокси видит реквизиты аутентификации, адрес туннеля и параметры трафика, поэтому административный список содержит только доверенных поставщиков. [RFC 9110, Proxy-Authorization](https://www.rfc-editor.org/rfc/rfc9110.html#section-11.7.2)

Тестовый TLS-прокси проверяет, что в `CONNECT` передаётся проверенный IP, а источник получает своё имя в `Host` и TLS. Перед развёртыванием применяют миграции Scout до `0015_proxy_auth_type`. Старые версии получают `auth_type: basic` без перешифрования; их привязка и реквизиты остаются совместимыми. В развёртывании режим включается через `SCOUT_PROXY_ENABLED=1` после согласования доступа и хранения данных. `SCOUT_PROXY_ENDPOINTS` задаёт JSON-словарь `IP:порт → TLS-имя`, с квадратными скобками вокруг IPv6. При выключенном режиме или отсутствии пары сервер блокирует подключение. Настройки `HTTP_PROXY` и `HTTPS_PROXY` для этого режима не используются. [urllib3, TLS через HTTPS-прокси](https://urllib3.readthedocs.io/en/stable/advanced-usage.html#http-and-https-proxies)

### Хранение реквизитов и доступ

- **PostgreSQL.** Профиль и его версии принадлежат `user_public_id`. Версия хранит IP, порт, метаданные и отдельный шифротекст с логином и паролем. Шифруем оба значения через Fernet с отдельным случайным ключом. Шифротекст связывает UUID версии и владельца с IP, портом и TLS-именем. При чтении эта привязка сверяется с текущей записью и списком разрешённых адресов. Клиентский ввод всегда шифруется заново. В режиме `none` шифруется та же привязка с парой JSON `null` вместо реквизитов; отдельный ключ требуется и для него. При расшифровке `basic` требует два допустимых реквизита, `none` — два `null`: подмена типа в БД блокируется, автоматического понижения режима нет. Пустой, повреждённый или открытый текст в поле секрета вызывает отказ.
- **Ключи.** Через секреты развёртывания передаются `SCOUT_PROXY_KEYS`, JSON-словарь ключей Fernet по идентификаторам, и `SCOUT_PROXY_ACTIVE_KEY`, идентификатор ключа записи. В БД хранится `key_id` и шифротекст. Ключи хранятся отдельно от дампов БД и резервных копий. Для ротации добавьте новый ключ, сделайте его активным и запустите `python -m src.manage scout_rotate_proxy_keys`. Старый ключ убирают после перешифрования и проверки актуальных резервных копий. Ошибка доступа к ключу блокирует использование профиля. [OWASP, управление секретами](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)
- **Права.** Создание, просмотр метаданных, смена и отзыв профиля требуют прав настройки и владения. Воркер перед соединением проверяет соответствие владельца запуска или снимка, версии профиля и её состояния. Администратор управляет списком разрешённых адресов и может отозвать профиль. Операции чтения реквизитов через пользовательский API отсутствуют.
- **Срок жизни.** После замены новые планы выбирают новую версию. Уже выполняющийся запуск может завершиться на закреплённой версии до явного отзыва. При отзыве версии или удалении владельца блокируются новые обращения и удаляется шифротекст. Старые версии без активных ссылок теряют шифротекст после завершения работы. В истории остаётся UUID и безопасные метаданные. Для нового запуска с действующей версией нужен подтверждённый план с её UUID. Для резервных копий действует срок хранения развёртывания, при восстановлении применяются актуальные отзывы.
- **Раскрытие.** API принимает открытый ввод для шифрования, воркер расшифровывает его в памяти для подключения. Публичный план, ответы, задачи и результаты Celery, журнал, Evidence, экспорт и URL содержат только разрешённые поля. Тело записи реквизитов, `Proxy-Authorization` и сетевые исключения фильтруются до записи в логи и трассировку. В аудите достаточно идентификаторов, действия, результата и `request_id`. В браузере реквизиты остаются в форме до отправки, долговременное хранилище браузера для них не используется.

Проверка существующего `secret_box` показала, что строковый интерфейс допускает старый открытый текст и считает вход с префиксом `enc:v1:` уже зашифрованным. Кроме того, его ключ производен от Django `SECRET_KEY`. Для нового хранилища прокси нужны строгий формат и отдельный ключ, поэтому этот интерфейс нельзя подключить напрямую.

### Отказ прокси

- `proxy_unavailable` — соединение отклонено, истёк сетевой таймаут или прокси вернул `502`, `503` или `504` на `CONNECT`. До трёх попыток суммарно с паузами 1 и 3 секунды в пределах бюджета запуска. В режиме прокси у запуска одна активная загрузка или одна загрузка в ожидании повтора. Это удерживает остальные загрузки в очереди до исхода повторов.
- `proxy_auth_failed` — ответ `407` в любом режиме. Попытки прекращаются без прямого подключения и без автоматического перехода на Basic. Пользователь может явно заменить тип авторизации и реквизиты и подтвердить план с новой версией. [RFC 9110, 407](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.8)
- `proxy_tls_error`, `proxy_blocked`, `proxy_credentials_unavailable` — окончательные ошибки до отправки реквизитов или запроса к сайту. Пользователь получает сообщение по коду. HTTP-ошибки сайта после установки туннеля остаются ошибками источника.

При окончательной ошибке Scout прекращает постановку новых загрузок для этого запуска. Завершённые результаты сохраняются, обработка уже принятых снимков может закончиться. Итог — `completed_with_errors` при наличии пригодных снимков основного сбора или результатов, иначе `failed`. Пауза и отмена продолжают определяться состоянием запуска. Предпросмотр показывает безопасную ошибку загрузки. Прямой режим и другой профиль доступны только как явное изменение плана с новым подтверждением.

### Данные и результаты проверки

- HTML основного сбора хранится файлами в кэше Scout. Визуальные снимки лежат в PostgreSQL, срок доступа — один час, очистка выполняется Beat. Реализованная [политика SCALE-001](#scale-001--сроки-хранения-и-очистка) задаёт начальные сроки HTML 30 суток, комплекта результата с Evidence 365 суток и выгрузок 7 суток. Последние два результата и активные сборы защищены, предварительный просмотр показывает последствия удаления. Автоматическая очистка по умолчанию выключена; её включение и сроки выбирает администратор. Снимки с общим хешем удаляются только после исчезновения последней ссылки.
- `Record` и `Evidence` хранятся в PostgreSQL. JSON и CSV отдаются через Media API по подписанной ссылке после проверки прав в Scout. Истечение подписи ограничивает скачивание, а удаление файла требует отдельной операции. Профили и ключи хранятся отдельно от снимков, строк и выгрузок. Доступ к каталогам снимков, выгрузкам и резервным копиям ограничивается сервисными учётными записями. В журнале и телеметрии подписанная ссылка считается временным секретом.
- Обнаружен отдельный риск данных. Локальный пример подтвердил, что текст `=1+1` из HTML попадает в CSV как есть. При открытии в табличном редакторе такой текст может интерпретироваться как формула. Исправление требует отдельной проверки формата для табличного редактора и совместимости выгрузок. [OWASP, CSV Injection](https://community.owasp.org/attacks/CSV_Injection)

Тесты прокси используют реальные локальные сокеты и отдельные сертификаты прокси и источника. Проверены успешное соединение, 407, три попытки при недоступности, медленный `CONNECT`, неверное TLS-имя, чужой UUID, отзыв и ротация ключа. Внутреннее назначение и редирект к облачным метаданным блокируются перед созданием туннеля. Ответы, журналы и сообщения Celery проверены на контрольные реквизиты, включая Basic-заголовок. Для теста реального поставщика потребуется разрешённый внешний адрес.

## AI-001 — черновик плана по описанию

Серверная операция доступна при `SCOUT_AI_ENABLED=true` в окружении Django и настроенной модели модуля `ollama_framework`. Scout вызывает `ollama_framework.chat` через мост ERGOMS с отключённым режимом рассуждений. Необязательный `SCOUT_AI_MODEL` выбирает установленную модель отдельно для Scout: она передаётся в `config.model` с `skip_env_injection=true`, чтобы общая модель провайдера её не заменила. Пустое значение сохраняет модель по умолчанию `ollama_framework`; параметры других потребителей не меняются. В первом сценарии пользователь даёт одну открытую HTML-страницу и описывает поля. Модель предлагает правила, Scout проверяет их на примере, а пользователь может отредактировать и сохранить результат как обычный план.

### Запрос на предложение

На стенде используем [тестовый каталог DATA-001](../api/tests/fixtures/data001_catalog.html) с тремя карточками. Его можно раздать командой из корня ERGOMS `python -m http.server 8765 --bind 127.0.0.1 --directory modules/scout/api/tests/fixtures`. В настройках стенда добавляем `SCOUT_TRUSTED_FETCH_ENDPOINTS=127.0.0.1:8765`. В приёмке предложения ответ модели задаёт тестовый адаптер.

1. Действующий `POST visual-snapshots/` принимает `{"url":"http://127.0.0.1:8765/data001_catalog.html"}`. Получаем `public_id` и ждём `status: "ready"` через `GET visual-snapshots/{public_id}/`.
2. `POST plan-suggestions/` принимает UUID этого снимка и текст цели. Запрос требует аутентификации и `scout_configure`. Для загрузки снимка отдельно требуется `scout_run`.

```json
{
  "snapshot_public_id": "20000000-0000-4000-8000-000000000001",
  "goal": "Собери ровно три поля: название товара, цену в рублях и остаток в штуках. Одна строка на карточку."
}
```

Используем только готовый снимок текущего пользователя с действующим сроком доступа. Цель после удаления пробелов по краям должна содержать от 1 до 2 000 символов. Сервер берёт из снимка структурный фрагмент до 32 КиБ в UTF-8 с тегами, классами, идентификаторами и текстом. Содержимое страницы передаётся модели как данные. Скрипты, формы, реквизиты прокси и служебные данные пользователя исключаются. Scout отправляет один запрос на предложение без сетевых инструментов модели. По умолчанию сервер ждёт 15 секунд. Оператор может задать от 1 до 60 секунд через `SCOUT_AI_TIMEOUT_SECONDS` с учётом таймаутов клиента и шлюза. Один процесс Django держит до двух вызовов модели. При исчерпании мест Scout возвращает `503 model_unavailable`. Вызов, который ещё выполняется у провайдера, удерживает место до завершения. Локальная конфигурация проверена после перезапуска в [рабочем проекте](IMPLEMENTATION_STATUS.md#постоянное-подключение-в-рабочем-проекте). Выбор для других установок остаётся в [Q-007](OPEN_QUESTIONS.md#q-007--какие-возможности-обязательны-у-настроек-с-llm).

### Черновик плана

При успехе HTTP 200 возвращает UUID проверочного снимка и `draft` в формате тела `POST jobs/`. Сервер берёт `seed_urls` из исходного адреса снимка и задаёт `crawl.mode: "pages"`. Если снимок загружен через прокси, сервер переносит закреплённый UUID версии профиля из снимка в `draft.proxy_profile_revision_public_id`. Модель предлагает только `record` и `fields`. Название пользователь может добавить перед сохранением. Предложение не создаёт задание, версию плана или запуск.

```json
{
  "snapshot_public_id": "20000000-0000-4000-8000-000000000001",
  "draft": {
    "seed_urls": ["http://127.0.0.1:8765/data001_catalog.html"],
    "crawl": {"mode": "pages"},
    "record": {"kind": "css", "selector": "article"},
    "fields": [
      {"name": "name", "kind": "css", "selector": "h2", "scope": "record", "many": false},
      {"name": "price", "kind": "css", "selector": ".price", "scope": "record", "many": false,
       "conversion": {"type": "money", "currency": "RUB", "decimal_separator": ","}},
      {"name": "quantity", "kind": "css", "selector": ".quantity", "scope": "record", "many": false,
       "conversion": {"type": "integer"}}
    ]
  }
}
```

Перед выдачей черновика сервер проверяет структуру ответа модели, нормализует общий план и применяет правила штатным извлекателем к исходному снимку с теми же областями `page` и `record`. Правило карточки должно найти хотя бы одну карточку, а каждое поле — хотя бы одно совпадение в своей области по всему примеру. Ноль совпадений в отдельной карточке допустим. Пустой текст и ошибка преобразования относятся к результату извлечения по DATA-001. После проверки совпадений пользователь сверяет смысл полученных значений в предпросмотре.

### Проверка обычным предпросмотром

1. После правок отправляем `draft` в `POST jobs/` или полный план в `PATCH jobs/{job_public_id}/`. Сохранённая `revision` содержит `plan_hash`.
2. Вызываем `POST jobs/{job_public_id}/explore/` с `{}`. Ответ HTTP 202 содержит `public_id` запуска. Читаем полный `GET runs/{run_public_id}/?value_format=typed_v1` до `awaiting_confirmation` или `failed`. Это новая загрузка источника по сохранённому плану.
3. В `preview` ожидаем три строки с `source_url`, `values` и `evidence`. Для `1-1` цена равна `{"amount":"1234.50","currency":"RUB"}`, остаток равен числу `0`. У `1-2` цена имеет `typed.status: "empty"`, а остаток — `"missing"`. У `1-3` оба поля имеют `"invalid"`, с кодами `invalid_decimal` и `invalid_integer`. Для существующих совпадений Evidence показывает локатор исходного элемента, например `css:.price#0.0` для первой цены.
4. Интерфейс предлагает подтверждение после проверки `preview`, `job_public_id` и `plan_hash` сохранённого плана. При правке после предпросмотра завершаем старый запуск через `POST runs/{run_public_id}/cancel/`, сохраняем новую версию и повторяем предпросмотр. `approve/` и `start/` вызываются для проверенного запуска по явному действию пользователя. Сбор использует сохранённые правила без вызовов модели.

### Ошибки и приёмка

- **HTTP 503 `model_unavailable`**. Поставщик недоступен, все места заняты, истекло время ожидания или интеграция отключена. Пример ответа `{"code":"model_unavailable","detail":"Модель временно недоступна. Повторите запрос или настройте поля вручную."}`. Сохраняем введённую цель и правки в форме, чтобы пользователь мог повторить запрос или продолжить вручную.
- **HTTP 502 `invalid_model_response`**. Поставщик ответил, но результат невозможно прочитать или привести к схеме плана. API возвращает `code` и `detail` без исходного ответа поставщика.
- **HTTP 422 `selector`**. Правило не поддерживается или не применяется. Для `.price[` пример ответа `{"code":"selector","detail":"Селектор не применился","path":"/fields/1/selector"}`. `path` указывает на правило внутри `draft`. Для правила карточки используется `/record/selector`.
- **HTTP 422 `selector_no_match`**. Селектор допустим, но на всём снимке даёт ноль совпадений. Например, `.price-missing` для цены. Ответ использует те же поля `code`, `detail` и `path`. В обоих случаях `422` пользователь может повторить запрос с уточнённой целью или вручную задать правило. Ответ не выдаёт непроверенный черновик.
- **HTTP 400 `invalid`** для неверных входных данных, **HTTP 404** для чужого, просроченного или отсутствующего снимка, **HTTP 409 `snapshot_not_ready`** для снимка, который загружается или завершился ошибкой. Эти запросы не вызывают модель.

Приёмка на каталоге проверяет успешный ответ тестового адаптера и все три строки штатного предпросмотра. Адаптер отдельно возвращает ошибку доступности, `.price[` и `.price-missing`, чтобы проверить три соответствующих ответа и возможность ручной настройки. Если пользователь сам изменил селектор на `.price[` после получения черновика, штатный `GET runs/{run_public_id}/` возвращает HTTP 200 с `preview.error.code: "selector"`. При корректном селекторе карточки и правиле `.price-missing` типизированный предпросмотр вернёт три строки с `values.price.typed.status: "missing"`. Интерфейс предлагает исправить правило и повторить проверку перед подтверждением.

### ИИ по нескольким типам страниц

Тот же `POST plan-suggestions/` принимает альтернативное тело с `pages` вместо одиночного `snapshot_public_id`. Требуются 2–5 готовых снимков, по одному на уникальный тип; хотя бы один тип извлекает данные. Пример:

```json
{
  "goal": "Название и цена товара в рублях",
  "pages": [
    {
      "snapshot_public_id": "20000000-0000-4000-8000-000000000001",
      "id": "catalog",
      "action": "discover",
      "match": [{"kind":"prefix","pattern":"/catalog/"}]
    },
    {
      "snapshot_public_id": "20000000-0000-4000-8000-000000000002",
      "id": "product",
      "action": "extract",
      "match": [{"kind":"prefix","pattern":"/products/"}]
    }
  ]
}
```

Для этого режима верхний уровень содержит только `goal` и `pages`; смешивать его с одиночным UUID нельзя. Владение, TTL один час и готовность проверяются для каждого снимка, в том числе после получения аренд чтения. Все исходные и конечные адреса должны иметь один канонический хост, все снимки — одну и ту же версию профиля прокси либо все прямое подключение. Повтор UUID, неверное число примеров, разные хосты и неверные поля дают HTTP 400 `invalid_snapshot_set`; чужой, отсутствующий или просроченный UUID — HTTP 404; неготовый снимок — HTTP 409 `snapshot_not_ready`; разные профили — HTTP 409 `snapshot_proxy_mismatch`.

Пользователь задаёт `id`, `action` и `match` по существующему контракту SPEC-002. Каждый пример должен однозначно соответствовать своему типу по конечному URL. Конфликт или несоответствие блокирует предложение до вызова модели: HTTP 409 `page_type_preview_blocked` с `snapshot_public_id` и `page_type_id`. Некорректные определения типов используют HTTP 400 `invalid_page_types`.

Один вызов модели получает цель и очищенные HTML-примеры; не больше 32 КиБ на пример и 64 КиБ суммарно. Реквизиты прокси, токены, содержимое других снимков и сетевые инструменты не передаются. Модель предлагает общий `record`, общие `fields` и отдельные `selectors` каждого извлекающего типа. Имена полей описывают смысл, а не классы HTML: `.price` и `.cost` разных типов могут заполнять общее поле `price`. Модель не меняет действия, границы URL, идентификаторы типов, прокси или лимиты. Формат ответа поставщика строго проверяется; пропущенное поле схемы, лишний/переименованный тип и изменение границ не принимаются как готовый план. Повтор определения одного имени объединяется только при совпадении всех свойств, кроме селектора и его языка; отличающиеся преобразования, валюта, область или кратность дают `invalid_model_response`. Переопределение селектора для каждого типа остаётся обязательным.

Перед HTTP 200 сервер нормализует весь план и проверяет каждое поле на примере каждого извлекающего типа. Ответ — `{"snapshot_public_ids":["UUID-1","UUID-2"],"draft":{...}}`. `draft` имеет формат `POST jobs/`: режим `site`, семена из снимков `discover` (если их нет — из всех примеров), контрольные адреса всех примеров и `preview_pages`, равный их числу. `crawl.page_types` сохраняет заданные пользователем роли и фильтры с проверенными селекторами модели. Общий `record` один для всех типов, как в текущем SPEC-002; разные селекторы контейнера карточек для разных типов этим расширением не добавляются. Профиль прокси переносится, как в одиночном режиме.

Ошибки модели сохраняют HTTP 503 `model_unavailable` и HTTP 502 `invalid_model_response`. Для неверного либо не находящего совпадений селектора возвращается HTTP 422 `selector`/`selector_no_match`, а также `snapshot_public_id`, `page_type_id` и путь вида `/crawl/page_types/1/selectors/price/selector`; для общего контейнера — `/record/selector`. Ошибка определения поля общей схемы сохраняет путь `/fields/N/selector` и указывает первый извлекающий пример. Непроверенный черновик не возвращается. Успешное предложение также не создаёт Job/Run и не подтверждает план.

Затем применяются обычные сохранение, предпросмотр, подтверждение хеша и запуск. Предпросмотр использует свежие контрольные страницы; предложение не подменяет проверку перед сбором. Проверка совпадений селектора не гарантирует верность преобразования: пользователь сверяет типизированные значения и при необходимости исправляет, например, десятичный разделитель цены. Ошибка доступности модели оставляет ручной и визуальный способы настройки; ни извлечение, ни повторный запуск, ни расписание не вызывают ИИ для обработки страниц. Прежнее тело с одним `snapshot_public_id` и прежний ответ сохранены. Миграция не требуется; клиентское подключение относится к FRONTEND.

## SPEC-002 — правила для типов страниц

План обхода может задавать типы страниц с отдельными селекторами. В плане без типов сервер использует один набор `fields` и `record` на весь запуск, а фильтр `extract_on` определяет, к каким страницам его применить.

### План и выбор типа

`POST jobs/` и `PATCH jobs/{job_public_id}/` принимают необязательный `crawl.page_types` для `mode: "site"`. Ответ задания возвращает нормализованный массив в `revision.crawl.page_types`, ответ запуска возвращает его в `crawl.page_types`. Если поле отсутствует, действует прежний формат плана, включая `extract_on`. При редактировании передаётся весь план, включая `crawl`.

- Массив содержит от одного до пяти типов, включая хотя бы один с действием `extract`. `id` уникален в плане и использует строчные латинские буквы, цифры и подчёркивание, начинается с буквы и содержит до 41 символа.
- У каждого типа есть непустой список `match`. Элементы имеют текущий формат `{kind, pattern}`. `prefix` проверяет начало пути, `contains` ищет строку во всём URL. Достаточно совпадения с одним условием внутри типа. Сопоставляется нормализованный конечный URL снимка после редиректа, с обычными правилами `drop_query`.
- `action: "discover"` оставляет страницу источником ссылок. `action: "extract"` дополнительно применяет селекторы к снимку. `selectors` у извлекающего типа — необязательный объект с именами полей из общего `fields` и парами `{kind, selector}` для переопределения. Поля без переопределения используют общий селектор. Порядок полей, `record`, `scope`, `many` и `conversion` общие, поэтому записи разных типов имеют одну схему и одни колонки CSV.
- В плане с типами извлечение определяет `page_types`, поэтому одновременно передать непустой `extract_on` нельзя. Пустой массив типов, неизвестное поле в `selectors` и другие ошибки структуры дают HTTP 400 с `code: "invalid_page_types"`, `detail` и `path`, например `/crawl/page_types/1/selectors/cost`. Пересечения правил проверяются на фактических URL.

Основной сбор по-прежнему начинается после подтверждения хеша сохранённой версии. `page_types` и переопределения входят в `plan_hash`. Все этапы пользуются одной версией правил. Новый URL попадает в существующую очередь из семени, карты сайта или HTML-ссылки, проходит сетевые проверки, фильтр `visit` и лимиты, затем загрузчик сохраняет HTML. На сохранённом снимке сервер выбирает тип и решает, нужен ли разбор полей. Извлекатель читает снимок и выбранные селекторы, сохраняет `Record` и `Evidence`. Выдача и экспорт читают сохранённый результат. Переходы из HTML ограничены общей политикой обхода и глубиной. Логика выбора типа одинакова в предпросмотре и основном сборе.

- Один тип `discover` даёт `discovery_only` и ноль строк. Основной сбор сохраняет снимок и обрабатывает ссылки.
- Один тип `extract` даёт `extracted` со строками или `no_records`. Основной сбор применяет выбранные селекторы и обрабатывает ссылки. Ноль строк фиксируется в журнале как предупреждение.
- При отсутствии типа предпросмотр возвращает `unmatched` и ноль строк. Основной сбор сохраняет снимок и обрабатывает допустимые ссылки.
- При совпадении нескольких типов предпросмотр возвращает `ambiguous` со списком типов. Основной сбор фиксирует ошибку страницы `page_type_ambiguous`, оставляет её ссылки в обходе и продолжает обработку остальных страниц.

У неоднозначной страницы нет записей. Если в основном сборе возникла такая ошибка, итоговый статус учитывает её как `completed_with_errors`. Порядок типов в массиве не определяет приоритет. Повторная доставка задачи использует тот же снимок и версию правил и не добавляет дубли.

Для извлекающей страницы `no_records` означает ноль контейнеров карточки или отсутствие фактических совпадений по всем настроенным полям. Пустой текст в найденном элементе считается совпадением. Когда хотя бы одно поле строки найдено, остальные могут быть пропущены или содержать ошибку преобразования по DATA-001. Evidence ссылается на использованный селектор и исходный снимок. Для планов с типами `rules_revision_public_id` в типизированном ответе относится к версии всего набора правил, включая переопределения. Форматы записей, Evidence и выгрузок сохраняются.

### Запрос и предпросмотр на тестовом каталоге

Тестовый источник содержит каталог `/catalog/` со ссылками на `/products/a`, `/products/a#duplicate` и `/products/b`. Каталог содержит заголовок `<h1>Каталог</h1>`. На странице `a` ожидается HTML `<h1>Чайник</h1><span class="price">1 250,00 ₽</span><span class="stock">3</span>`, на странице `b` — `<h1>Термос</h1><span class="price">790,00 ₽</span><span class="stock">0</span>`. Адрес `catalog.example` в примере заменяется адресом тестового сервера.

```json
{
  "title": "Тестовый каталог",
  "seed_urls": ["https://catalog.example/catalog/"],
  "record": null,
  "fields": [
    {"name":"title","kind":"css","selector":".product-name","scope":"page","many":false},
    {"name":"price","kind":"css","selector":".price","scope":"page","many":false,
     "conversion":{"type":"money","currency":"RUB","decimal_separator":","}},
    {"name":"quantity","kind":"css","selector":".stock","scope":"page","many":false,
     "conversion":{"type":"integer"}}
  ],
  "crawl": {
    "mode":"site",
    "max_depth":1,
    "max_pages":10,
    "visit":[{"kind":"prefix","pattern":"/catalog/"},{"kind":"prefix","pattern":"/products/"}],
    "preview_urls":["https://catalog.example/catalog/","https://catalog.example/products/a"],
    "preview_pages":2,
    "page_types":[
      {"id":"catalog","match":[{"kind":"prefix","pattern":"/catalog/"}],"action":"discover"},
      {"id":"product","match":[{"kind":"prefix","pattern":"/products/"}],"action":"extract",
       "selectors":{"title":{"kind":"css","selector":"h1"}}}
    ]
  }
}
```

`POST jobs/{job_public_id}/explore/` ставит в очередь только контрольные адреса и возвращает HTTP 202. Полный `GET runs/{run_public_id}/?value_format=typed_v1` при `awaiting_confirmation` сохраняет плоский массив `preview` со строками и Evidence и добавляет `page_type_preview` для плана с типами. `page_type_preview.pages` содержит результат на каждый контрольный URL, включая страницы с нулём строк. Ниже фрагмент ответа.

```json
{
  "status": "awaiting_confirmation",
  "page_type_preview": {
    "pages": [
      {"source_url":"https://catalog.example/catalog/","final_url":"https://catalog.example/catalog/",
       "type_ids":["catalog"],"outcome":"discovery_only","row_count":0,"error":null},
      {"source_url":"https://catalog.example/products/a","final_url":"https://catalog.example/products/a",
       "type_ids":["product"],"outcome":"extracted","row_count":1,"error":null}
    ],
    "unverified_extract_type_ids": [],
    "can_approve": true
  }
}
```

Строки `preview` связываются со страницей по `source_url`. В ответе примера одна строка для «Чайник» с ценой `{"amount":"1250.00","currency":"RUB"}` и количеством `3`. `record_count` до основного сбора равен нулю. `error` страницы равен `null` или объекту `{code, detail}`. При ошибке загрузки или разбора возвращаются `outcome: "error"` и `row_count: 0`. При ошибке загрузки также возвращаются `final_url: null` и `type_ids: []`. Если ни один контрольный снимок не загрузился, сохраняется статус запуска `failed` с `error_summary` и подробностями задач загрузки. При неоднозначности возвращаются `outcome: "ambiguous"`, `error.code: "page_type_ambiguous"` и все совпавшие типы в `type_ids`.

В `unverified_extract_type_ids` перечисляются извлекающие типы без контрольной страницы с хотя бы одной строкой. `can_approve` равно `true`, когда список пуст и среди контрольных адресов нет ошибок или неоднозначных типов. Сервер проверяет то же условие при `POST runs/{run_public_id}/approve/` и возвращает HTTP 409 с `code: "page_type_preview_blocked"`, если проверка не пройдена. `start/` проверяет подтверждение версии и состояние предпросмотра этого запуска. Правка типа, селектора или контрольного адреса требует новой версии и повторного предпросмотра. Компактный ответ `?summary=1` не включает `preview` и `page_type_preview`.

### Сценарии приёмки

1. Пройти создание, предпросмотр, подтверждение и сбор на примере. Проверить две записи с тремя Evidence на каждую, ноль записей с каталога, один fetch для `/products/a`, нулевое количество у «Термоса» и совпадение записей в API, JSON и CSV. Для названия Evidence должен содержать локатор `css:h1#0.0`. Проверить прежний план без `page_types`.
2. Добавить второй извлекающий тип с другой разметкой, переопределить селектор и проверить те же колонки результата. Без его контрольного URL подтверждение блокируется. Проверить также неверный селектор, валидный селектор с нулём совпадений и отсутствующее отдельное поле в строке с другими совпадениями.
3. Проверить два пересекающихся типа на контрольном URL и на URL, который встречается только в основном сборе. В первом случае подтверждение блокируется. Во втором остаются записи с остальных страниц и видна ошибка. Для URL без типа проверить обход его допустимых ссылок без создания записи.
4. Проверить редирект между типами, дубли URL из ссылок и карты сайта, повтор задачи извлечения и изменение хеша при редактировании правил.

## SPEC-001 — идентичность товара

Профиль идентичности позволяет объединять наблюдения одного товара в запуске. Для планов без профиля `Record.identity_key` по-прежнему защищает запись от повтора в пределах снимка и версий схемы и правил.

### План и ключ товара

`POST jobs/` и полный `PATCH jobs/{job_public_id}/` принимают необязательный объект `identity` верхнего уровня. Для первого профиля нужны `kind: "sku"`, `namespace` и `field`. `namespace` обозначает каталог в задании и содержит от 1 до 64 строчных латинских букв, цифр, дефисов или подчёркиваний, начиная с буквы. `field` ссылается на текстовое поле из `fields` с `many: false` и без `conversion`. Поле может быть общим для страницы или относиться к карточке. Один и тот же профиль применим к ручному, визуальному и текстовому способам настройки. В SPEC-002 типы страниц могут выбирать разные селекторы для одного и того же поля SKU.

Объект возвращается в `revision.identity` задания и входит в `plan_hash`. Неверная конфигурация даёт HTTP 400 с `code: "invalid_identity"`, `detail` и `path` до ошибочного поля. Планы без `identity` сохраняют прежние хеши, форму ответа и группировку по снимку.

Ключ вычисляется до преобразований DATA-001 и до усечения текста. Scout убирает внешние пробелы из единственного текстового совпадения SKU. Регистр, ведущие нули и внутренние пробелы сохраняются. Непустой SKU до 200 символов даёт стабильный `entity_key`. Это SHA-256 от компактного JSON-массива в UTF-8 `["sku-v1", job_public_id, namespace, field, sku]` с UUID задания в нижнем регистре и без экранирования Unicode. Ключ сравнивается в рамках одного задания и каталога. Правка цены, названия или селектора сохраняет ключ, если исходное значение SKU, имя поля и каталог остались прежними.

У каждой строки плана с идентичностью есть `identity.status`:

- `resolved` при одном непустом допустимом SKU. Все наблюдения с тем же ключом образуют одну строку в пределах запуска.
- `missing`, если совпадений нет или единственное совпадение пустое после обрезки пробелов.
- `ambiguous`, если селектор вернул больше одного совпадения, даже когда тексты совпали. Проверка происходит до выбора первого значения обычным скалярным полем.
- `invalid`, если единственное непустое значение превышает 200 символов или XPath вернул число либо логическое значение.

Для трёх последних статусов `entity_key` равен `null`. Строка остаётся в результате с Evidence найденных полей. Повтор обработки того же снимка и номера карточки не создаёт дубль. Строки без ключа с разных страниц остаются раздельными, даже при одинаковом названии или URL назначения. URL служит адресом источника. Без надёжного ключа Scout не связывает строки между запусками.

### Строка результата и Evidence

`Job` задаёт границу сравнения. `JobRevision` закрепляет план, схему, правила и профиль идентичности. `Run` хранит отдельный результат выполнения этой версии. `Task` обрабатывает снимок `PageSnapshot` и может повториться. `Record` хранит строку результата одного запуска и имеет собственный `public_id`. `Evidence` связывает наблюдаемое поле с записью, исходным снимком, локатором и версией правил.

Из наблюдений одного SKU в запуске Scout выбирает одну строку целиком. Для сравнения по порядку используются нормализованный конечный URL, нормализованный исходный URL, номер карточки с нуля, хеш снимка и исходный URL как сохранён в снимке. Если URL нельзя нормализовать для сравнения, используется его сохранённое значение. Строки и хеши сравниваются лексикографически, номер карточки — численно. Порядок выполнения задач и время ответа сайта не влияют на выбор. `identity.conflicting_fields` содержит имена полей в порядке схемы, где есть разные непустые значения. Для преобразованного поля сравниваются значения со статусом `ok`, для текстового — нормализованный текст. Пропуск, пустой текст или ошибка преобразования остаются видны как состояния и не образуют конфликт значений.

Evidence сохраняется по каждому фактическому совпадению из всех наблюдений, включая совпадающие цены с разных страниц. В нём остаются `source_url`, `snapshot_public_id`, `rules_revision_public_id`, `field_path`, `locator`, исходное и нормализованное значения, идентификатор и версия извлекателя. Для преобразованного значения Evidence хранит и результат преобразования по DATA-001. `selected: true` указывает, что это наблюдение дало показанную строку. Остальные совпадения получают `selected: false`. При смене выбранного наблюдения Evidence предыдущего источника остаётся у той же строки. Если поле пропущено в выбранной строке, совпадение с другой страницы доступно в Evidence своего наблюдения. Пропущенный элемент не создаёт Evidence.

База ограничивает уникальность пары «запуск, ключ товара» у строк с SKU. Запись без SKU использует ключ наблюдения из снимка и номера карточки в рамках запуска. Для Evidence ключ повтора включает строку результата, снимок, номер карточки, поле и локатор. Выбор наблюдения и добавление Evidence выполняются в одной транзакции под блокировкой запуска. Поля и ограничения создаёт миграция Scout `0012_product_identity`.

### Запрос и контрольный каталог

Тестовое задание с `job_public_id: "10000000-0000-4000-8000-000000000001"` использует один каталог `demo_catalog`. Для теста обе страницы SKU `K-01` и страницы остальных товаров отдаются с заголовком `h1`, текстовым SKU в `.sku` и ценой в `.price`. На странице без SKU элемент `.sku` отсутствует.

```json
{
  "title": "Контрольный каталог",
  "seed_urls": [
    "https://catalog.example/products/k-01",
    "https://catalog.example/sale/k-01",
    "https://catalog.example/products/k-02",
    "https://catalog.example/products/no-sku"
  ],
  "record": null,
  "fields": [
    {"name":"sku","kind":"css","selector":".sku","scope":"page","many":false},
    {"name":"title","kind":"css","selector":"h1","scope":"page","many":false},
    {"name":"price","kind":"css","selector":".price","scope":"page","many":false,
     "conversion":{"type":"money","currency":"RUB","decimal_separator":","}}
  ],
  "identity": {"kind":"sku","namespace":"demo_catalog","field":"sku"}
}
```

- `/products/k-01` и `/sale/k-01` возвращают «Чайник», SKU `K-01` и цену `1 250,00 ₽`. Это одна строка, выбранная из `/products/k-01`, с шестью Evidence, по три с каждой страницы.
- `/products/k-02` возвращает «Чайник», SKU `K-02` и цену `990,00 ₽`. Это отдельная строка с другим ключом, несмотря на то же название.
- `/products/no-sku` возвращает «Чайник» и цену `800,00 ₽`. Это отдельная строка с `identity.status: "missing"` и двумя Evidence. После первого сбора в результате три строки.
- Во втором запуске обе страницы `K-01` возвращают `1 350,00 ₽`. `entity_key` совпадает с первым запуском, а `Record.public_id`, снимки, Evidence и цена принадлежат второму запуску. Первый запуск по-прежнему отдаёт `1250.00`.

`POST jobs/{job_public_id}/explore/` сохраняет текущий путь предпросмотра. В полном `GET runs/{run_public_id}/?value_format=typed_v1` поле `preview` показывает результат группировки по загруженным контрольным снимкам. Отдельно считаются наблюдения со страницы для диагностики SPEC-002. Предпросмотр не создаёт итоговых `Record`. Отсутствие SKU показывает статус строки и само по себе не блокирует подтверждение. После `approve/` и `start/` полный набор строк доступен через `GET runs/{run_public_id}/records/?value_format=typed_v1`.

Фрагмент строки `K-01` из первого запуска показывает два Evidence по цене. Остальные поля и их Evidence входят в полный ответ.

```json
{
  "public_id": "40000000-0000-4000-8000-000000000001",
  "identity": {
    "status": "resolved",
    "entity_key": "a4c34330f906dc634f53b21cefbe320087a47be2fa68e0c177a14da3710e5300",
    "conflicting_fields": []
  },
  "values": {
    "price": {"raw":"1 250,00 ₽","normalized":"1 250,00 ₽",
              "typed":{"type":"money","status":"ok","value":{"amount":"1250.00","currency":"RUB"},"error":null}}
  },
  "evidence": [
    {"field_path":"price","source_url":"https://catalog.example/products/k-01","locator":"css:.price#0.0",
     "snapshot_public_id":"20000000-0000-4000-8000-000000000001",
     "rules_revision_public_id":"30000000-0000-4000-8000-000000000001",
     "raw_value":"1 250,00 ₽","normalized_value":"1 250,00 ₽",
```

Для задания с `identity` оба формата API и JSON содержат `identity` и признак `selected` в Evidence. `typed_v1` дополнительно выдаёт типизированные значения и идентификаторы снимка и правил. CSV сохраняет существующие колонки и показывает выбранную строку на товар. По `public_id` можно найти её Evidence в JSON этого запуска.

### Приёмка реализации

1. Проверить два запуска с указанным каталогом. В каждом три строки. Два SKU сохраняют ключи, строка без SKU имеет `entity_key: null`, история первого запуска сохраняет прежнюю цену. Сверить выдачу и подписанные выгрузки.
2. Поменять цену только на `/sale/k-01` на `1 300,00 ₽` в отдельном контрольном запуске. Строка показывает `1250.00`, `conflicting_fields` равно `["price"]`, оба Evidence содержат свои значения. Повторить в обратном порядке обработки и повторно доставить задачу. Состав строк и Evidence совпадает.
3. Проверить пустой, двойной и длинный SKU, регистр и ведущие нули. Отдельно проверить план без `identity` и доступ к чужому заданию.

Сравнение по ключу товара описано в [EXT-002](#ext-002--api-сравнения-запусков).

### Явные ключи без SKU

Профиль идентичности может явно использовать другое текстовое поле либо конечный URL страницы. Новых миграций нет: используются существующие `identity`, `entity_key`, состояние записи и Evidence. Без профиля прежний формат не объединяет записи. Автоматическое угадывание ключа по названию, цене или похожести отсутствует.

```json
{"identity":{"kind":"field","namespace":"supplier_catalog","field":"external_id"}}
```

`field` — одиночное текстовое поле общей схемы, без `conversion`. Оно может быть номером источника или другим выбранным пользователем устойчивым идентификатором, который не называется SKU. Правила совпадения прежние: ровно одно строковое значение, обрезаются пробелы по краям, регистр и внутренние пробелы сохраняются, максимум 200 символов. Отсутствие, пустота, несколько совпадений, числовой XPath-результат или слишком длинное значение оставляют наблюдение без ключа и не объединяют его с другими. Evidence сохраняется со всех наблюдений; одинаковые названия с разными ключами дают разные записи.

```json
{"identity":{"kind":"url","namespace":"article_catalog"}}
```

`url` разрешён только при `record: null`: одна запись на страницу. Поле `field` для него не принимается. Ключ строится из конечного URL снимка после HTTP-редиректов; при отсутствии конечного используется исходный URL. Канонизируются имя хоста/IDNA, стандартный порт и фрагмент; параметры из подтверждённого `crawl.drop_query` удаляются. Остальные параметры, путь и схема сохраняются, длина канонического адреса — до 2000 символов. Два адреса одного названия остаются разными объектами, если не приводят к одному конечному URL. `rel=canonical` из HTML не используется и не загружается. Для карточек каталога нужно выбрать явное поле ключа, а не объединять все карточки по URL страницы.

`entity_key` устойчив между запусками одного задания, пространства имён и профиля, но не объединяет разные задания или разные виды ключей. Для существующего `kind: "sku"` алгоритм хеша и формат ответа сохранены. Изменение профиля меняет `plan_hash`, требует нового предпросмотра/подтверждения и не переписывает историю.

Для новых профилей `record.identity` дополнительно содержит `kind` и `key_value` (для наблюдения без ключа — `null`). У URL нет выдуманного селектора: происхождение ключа — исходный/конечный адрес и UUID сохранённого снимка. Evidence извлекаемых полей остаётся прежним и сохраняется после очистки HTML.

Сравнение EXT-002 принимает оба новых профиля при прежних требованиях одинакового плана и завершённых запусков. В элементе изменения нового профиля вместо `sku` возвращается `key: {"kind":"field","value":"A-17"}` либо `key: {"kind":"url","value":"https://example.com/products/a"}`. Для SKU поле `sku` остаётся без изменения. Полнота, строки без ключа, конфликт значений и Evidence обеих сторон трактуются так же, как в сравнении SKU. Неверный профиль, ключ-массив, преобразование ключа и `url` с карточками дают HTTP 400 `invalid_identity`; несовместимые запуски — HTTP 409 `comparison_incompatible`.

## EXT-002 — API сравнения запусков

Пользователь вручную выбирает два сохранённых результата одного задания. Сервер сравнивает их по `entity_key` из SPEC-001. Расписание относится к отдельному этапу EXT-002.

### Запрос и условия

`GET /api/scout/runs/{target_run_public_id}/compare/?base_run_public_id={base_run_public_id}&field=price`

- `base_run_public_id` указывает на исходный запуск, а UUID в пути — на более поздний. Направление сравнения определяется временем начала основного сбора. Оба запуска принадлежат одному заданию, имеют одинаковый `plan_hash` и используют явный профиль `sku`, `field` или `url`.
- `field` — обязательное имя одного поля из схемы плана. В первом варианте поддерживаются одиночные текстовые поля и поля с преобразованием DATA-001. Для цены сравниваются точная сумма и валюта, для других преобразованных полей — типизированное значение, для текста — `normalized`. Форматирование и порядок Evidence на сравнение не влияют.
- Операция требует аутентификации, права просмотра Scout и доступа к обоим запускам по тем же правилам, что и `GET runs/{public_id}/records/`.
- `limit` от 1 до 200 задаёт число элементов `changes`, по умолчанию 50. `cursor` — непрозрачный курсор, привязанный к паре запусков и полю. Порядок — по `entity_key` по возрастанию. Счётчики относятся ко всему сравнению и повторяются на каждой странице. `next_cursor: null` означает конец списка.

Операция принимает `completed` и `completed_with_errors`. Полнота каждой стороны оценивается в пределах плана. `complete` означает `completed` без `stop_reason`. `partial` означает `completed_with_errors` или итог со `stop_reason`, например `max_pages` либо `time`. Ответ показывает `status`, `completeness`, `stop_reason` и число задач в окончательном состоянии `failed`. Действия по отменённым, неуспешным и ещё не завершённым запускам получают HTTP 409.

### Статусы сравнения

- `changed` — ключ найден в обоих запусках, у поля есть два пригодных значения и они различаются. Это изменение наблюдаемого значения. При частичном сборе оно может быть показано вместе с предупреждением о полноте.
- `unchanged` — ключ найден в обоих запусках, пригодные значения поля совпадают. Статус учитывается в счётчиках. Такие строки опускаются из `changes`.
- `uncertain` — ключ найден в обоих запусках, но хотя бы на одной стороне поле пустое, отсутствует, не преобразовалось или перечислено в `identity.conflicting_fields`. Ответ содержит доступные значения и Evidence. Пригодным считается непустой нормализованный текст или типизированное значение со статусом `ok`, в том числе ноль.
- `added` — ключ найден только в новом запуске, исходный результат полный. Метка означает появление товара в выдаче относительно исходного сбора.
- `not_seen_before` — ключ найден только в новом запуске, исходный сбор был частичным. Новизна товара не подтверждена.
- `not_seen` — ключ найден только в исходном запуске, новый сбор полный. Товар не найден в повторном результате в границах плана. Этот статус не подтверждает удаление товара на сайте.
- `not_checked` — ключ найден только в исходном запуске, новый сбор частичный. Товар не подтверждён повторным сбором.

Каждая строка без надёжного SKU учитывается в `unkeyed_records` своей стороны. Такие строки доступны в обычной выдаче запуска и не попадают в сравнение. `counts` содержит все семь статусов с нулями для пустых категорий. Сумма счётчиков равна числу разных ненулевых `entity_key` в обоих запусках.

В каждой строке `changes` есть `entity_key`, `sku` из выбранного наблюдения без внешних пробелов, `status`, `before` и `after`. Сторона без записи равна `null`. Существующая сторона содержит `record_public_id`, `value` в формате `typed_v1` или `null`, состояние поля `state` и массив `evidence` по выбранному полю. `state` равен `conflict`, если поле указано в конфликтах записи. Иначе для преобразованных полей берётся статус DATA-001, а для текста используются `ok`, `empty` при пустом совпадении выбранного наблюдения и `missing` при отсутствии совпадения в нём. Evidence возвращается в формате SPEC-001 с URL, снимком, версией правил, локатором и `selected`. Для каждой стороны возвращаются также совпадения с остальных страниц товара. В ответе остаются сохранённые значения и снимки соответствующего запуска.

### Контрольный каталог

Используем товары [SPEC-001](#spec-001--идентичность-товара). Начальная страница `/catalog/` перечисляет ссылки на товары, включая два URL `K-01`. Оба запуска используют один и тот же сохранённый план в режиме `site`. Контрольные страницы и фильтры сохраняются, а содержимое каталога на стенде меняется между сборами.

- HTTP 404, если любой запуск отсутствует или недоступен текущему пользователю. Проверка доступа выполняется до проверки совместимости.
- HTTP 409 `comparison_not_ready`, если статус любой стороны не входит в два допустимых. HTTP 409 `comparison_incompatible`, если у запусков разные задания, разные хеши плана или отсутствует поддерживаемый профиль идентичности. Ошибки Scout возвращают `code` и `detail`.

При приёмке проверить полный и частичный варианты на одинаковом плане, обе стороны Evidence и отдельные счётчики строк без SKU. Отдельно проверить частичный исходный сбор, конфликт цены, численно равные цены с разным форматированием, порции с `limit=1`, пустой список изменений и попытку сравнить недоступный запуск.

## EXT-002 — ежедневное расписание

Ежедневное расписание закрепляет подтверждённую версию плана и разрешение владельца запускать её автоматически. Один календарный день даёт не более одного запуска данного расписания. Модели расписания и истории создаёт миграция `0013_daily_schedules`.

### API и подтверждённый план

- `POST jobs/{job_public_id}/schedule/` создаёт одно расписание задания, HTTP 201. Повторное создание даёт HTTP 409 с `code: "schedule_exists"`. После неоднозначного сетевого ответа клиент читает расписание через GET.
- `GET jobs/{job_public_id}/schedule/` возвращает настройки, их версию и следующее время запуска. Если расписания ещё нет, возвращается HTTP 404.
- `PATCH jobs/{job_public_id}/schedule/` меняет переданные поля и возвращает HTTP 200. Поле `expected_version` обязательно. При несовпадении версии сервер возвращает HTTP 409 с `code: "schedule_changed"`. Успешная правка увеличивает `version`.
- `GET jobs/{job_public_id}/schedule/occurrences/?limit=50&cursor=...` возвращает историю назначенных дней с курсорной пагинацией. `limit` от 1 до 200, порядок по `local_date` и `public_id` от новых к старым. Курсор привязан к UUID расписания. `next_cursor: null` завершает выдачу. История включает пропуски.

Настройка требует доступа к заданию и прав `scout_configure` и `scout_run`. Чтение требует `scout_view` и доступа к заданию. Выполнение идёт от имени владельца задания. Клиент передаёт UUID версии и её `plan_hash`. Сервер проверяет принадлежность версии заданию и равенство `approved_plan_hash == plan_hash`. Включение расписания выражает согласие на последующие автоматические запуски этой версии.

```json
{
  "plan_revision_public_id": "60000000-0000-4000-8000-000000000001",
  "plan_hash": "a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1",
  "local_time": "09:00",
  "timezone": "Europe/Moscow",
  "enabled": true
}
```

Все пять полей обязательны при создании. `enabled` — JSON boolean. `local_time` — строка `HH:MM` с минутной точностью. `timezone` — доступное на сервере имя IANA. Сервер сохраняет его отдельно от часового пояса операционной системы. UUID версии и хеш меняются парой. Пример ответа на создание, если запрос принят 7 ноября 2026 года после 09:00 по Москве:

```json
{
  "public_id": "70000000-0000-4000-8000-000000000001",
  "job_public_id": "10000000-0000-4000-8000-000000000001",
  "version": 1,
  "plan_revision_public_id": "60000000-0000-4000-8000-000000000001",
  "plan_hash": "a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1",
  "local_time": "09:00",
  "timezone": "Europe/Moscow",
  "enabled": true,
  "start_window_seconds": 900,
  "next_scheduled_at": "2026-11-08T06:00:00Z"
}
```

Первая дата после создания, включения или изменения времени, часового пояса либо версии плана выбирается строго в будущем по серверному времени. Уже обработанная дата в этом расписании остаётся обработанной после правки или повторного включения. Для отключения подходит PATCH с `{"expected_version":1,"enabled":false}`. В отключённом состоянии `next_scheduled_at` равно `null`. Отключение предотвращает создание следующих запусков, а текущий запуск управляется обычными pause/resume/cancel.

Новая версия задания не меняет закреплённую версию расписания. Для перехода на неё пользователь проверяет предпросмотр, подтверждает хеш и явно обновляет привязку расписания. Диспетчер читает закреплённый UUID из БД. При подготовке очередного сбора загружаются новые контрольные снимки и выполняется обычная проверка. Если она проходит, координатор вызывает штатный старт по уже подтверждённой версии. Для SPEC-002 проверяются покрытие типов и конфликты. Ошибка загрузки, селектора или проверки завершает подготовку с `failed` и освобождает слот. Такой запуск не остаётся в ожидании ручного подтверждения.

### Календарь, занятый слот и пропущенные дни

Плановое время рассчитывается как календарная дата и `local_time` в сохранённой зоне. `scheduled_at` и время фактических событий в API выдаются в UTC. Если местное время отсутствует при переводе часов, дата отмечается пропущенной с `reason: "local_time_missing"` и `scheduled_at: null` после окончания разрыва местного времени. Если время встречается дважды, используется первое вхождение. Дата имеет одну запись истории. `next_scheduled_at` показывает ближайшее будущее существующее время, дата которого ещё не обработана.

В первой версии окно создания запуска фиксировано в 900 секунд. Для планового времени `scheduled_at` дата пригодна к запуску при `scheduled_at <= now < scheduled_at + 900 секунд`. В 09:15:00 местного времени окно запуска 09:00 закрыто. После этого история получает `status: "skipped"` и `reason: "missed"`.

При проверке пригодной даты координатор атомарно занимает общий слот Scout. Если другой запуск находится в `exploring`, `awaiting_confirmation`, `running`, `pausing`, `paused` или `cancelling`, дата получает `skipped` с `reason: "slot_busy"`. Повторное освобождение слота в тот же день не возвращает её к запуску. При одновременной готовности нескольких расписаний порядок определяется `scheduled_at`, затем UUID расписания.

Если ноутбук выключен несколько дней, после включения в истории появляются пропуски всех назначенных дат за время включённого расписания. Просроченные даты не создают сборов. Текущая дата может дать один сбор, если её окно ещё открыто и слот свободен. Для выключенного расписания новые даты истории не создаются. Если настройки сменились в открытом окне до создания запуска, прежняя дата получает `skipped` с `reason: "superseded"`. Разбор большого числа старых пропусков выполняется порциями по 100 дат и не задерживает обработку текущего окна.

Окно ограничивает создание нового `Run`. Уже созданный запуск после перезапуска восстанавливается по REL-001 с тем же UUID. Пауза, отмена, бюджет времени плана и сроки аренды продолжают определять его состояние.

### История и защита от дублей

Нужны сохраняемые сущности расписания и назначенного дня. У расписания есть владелец, ссылка на задание и версию плана, локальное время, зона, признак включения и номер версии настроек. Версии настроек сохраняют интервалы действия и включения, чтобы после простоя восстановить пропуски по действовавшему тогда времени. Запись назначенного дня сохраняет UUID расписания, его версию на момент назначения, локальную дату, `scheduled_at`, время обработки, состояние, причину и ссылку на запуск.

Уникальность пары «расписание, локальная дата» обеспечивается БД. У записи дня может быть не более одного `Run`. Захват даты, проверка глобального слота, создание запуска и его задач происходят в одной транзакции с блокировками. После коммита задачи передаются в обычную очередь Scout. Если публикация в брокер не удалась, существующая сверка найдёт задачи в БД. Повторное сообщение Beat или Celery продолжает тот же день и тот же запуск.

Статус дня принимает `preparing`, пока загружаются и проверяются контрольные страницы, затем `running`. Итоговые состояния `completed`, `completed_with_errors`, `failed` и `cancelled` отражают итог запуска. `skipped` имеет `run_public_id: null`. Связанная запись может находиться в `running`, пока пользователь держит сам запуск на паузе. Точное состояние читается через `GET runs/{run_public_id}/`.

Периодическая задача `dispatch_daily_schedules` проверяет расписания на существующем Beat каждые 30 секунд в очереди `scout`. Проверка текущей даты и восстановление после простоя используют одну и ту же запись дня. Сверка исполнения задач также работает каждые 30 секунд.

Если разрешение или ресурс отозваны, дата получает `skipped` с причиной `permission_revoked`, `plan_unapproved` либо `proxy_revoked`, а расписание отключается. Следующий запуск требует явного включения после исправления причины. Итоговые даты не запускаются заново.

### Ошибки и приёмка

HTTP 400 `invalid_schedule` с `code`, `detail` и `path` описывает неверное время, зону, UUID или структуру тела. HTTP 409 `schedule_changed` описывает конфликт версии настроек, `schedule_exists` — повтор создания, `approval_required` — неподтверждённую версию плана. Отсутствующая или недоступная версия/задание дают HTTP 404, недостаточные права — HTTP 403. История использует `invalid_limit` и `invalid_cursor` по обычным правилам пагинации Scout.

Для приёмки на контрольном каталоге выполнить две календарные даты, изменить цену между ними и проверить сравнение двух запусков с Evidence через действующий API EXT-002. Дополнительно проверить повторную проверку одной даты двумя диспетчерами, сбой до и после коммита, потерю публикации в брокер, занятый слот, включение ноутбука в 09:10 и в 09:25, несколько дней простоя, отключение и повторное включение, правку времени в тот же день и смену закреплённой версии. Перевод часов проверяется на зоне с отсутствующим и повторяющимся местным временем.

## SCALE-001 — сроки хранения и очистка

Статус на 7 ноября 2026 года: **серверная часть реализована**. Политику, закрепления, предварительный просмотр и возобновляемые задания очистки добавляет миграция `0014_retention_cleanup`. Новая автоматическая очистка по умолчанию выключена; существующая часовая очистка `VisualSnapshot` сохраняется. Рабочий лимит обхода остаётся 200 страниц. Проверки — в [статусе реализации](IMPLEMENTATION_STATUS.md#scale-001--очистка-по-срокам).

### Что хранится сейчас и что требуется изменить

`PageSnapshot` хранит метаданные в PostgreSQL, а HTML — в кэше `scout/snapshots/{sha256}.html`. Один файл может использоваться несколькими снимками, запусками и владельцами. `Record.snapshot` и `Evidence.snapshot` связаны с `PageSnapshot` через `CASCADE`: удалять строку снимка ради освобождения HTML нельзя. `VisualSnapshot.body` хранится отдельно, в PostgreSQL, и служит временным материалом настройки.

Выгрузка записывается через общий `MediaClient`; `ExportArtifact` хранит ссылку на неё. Сейчас повторные выгрузки одного формата могут ссылаться на один путь. Срок подписи ссылки, по умолчанию один час в ядре, не является сроком хранения файла. Сравнение EXT-002 вычисляется по `Record`, Evidence и данным запуска, отдельного сохранённого результата сравнения нет.

Реализация использует отдельные состояния доступности HTML, результата и выгрузки, учёт операций чтения/записи, политику владельца, закрепления и устойчивые задания очистки. Для сравнения после очистки HTML сохраняются значения, Evidence, метаданные снимков, версии схемы и правил, профиль SKU и исходная полнота запуска. Эти данные составляют неделимый **комплект результата**. API не выдаёт неполный комплект как обычный результат.

### Стартовые сроки и включение

Числа ниже — начальные значения первой реализации. Само применение миграции не включает автоматическое удаление. Политика одна на владельца; изменение политики не изменяет хеш подтверждённого плана и расписание сбора.

- `html_days: 30` — хранить HTML основного сбора и предпросмотра 30 суток после `Run.finished_at`. Метаданные `PageSnapshot` остаются вместе с результатом и ссылками Evidence. Для общего файла требуется разрешение очистки от всех ссылающихся снимков, а не только от самого старого.
- `result_days: 365` — хранить комплект результата 365 суток после `finished_at`, включая типизированные значения, строки без SKU, конфликты, все Evidence и версии правил. Evidence не имеет отдельного сокращённого срока.
- `export_days: 7` — хранить конкретный файл JSON/CSV семь суток после успешной записи. Пока комплект результата доступен, выгрузку можно создать заново без HTTP-загрузки источника и без ИИ. Новая выгрузка имеет новый UUID, неизменяемый путь с UUID артефакта и собственный срок; продлевать старый файл выдачей новой подписи нельзя.
- `visual_snapshot_hours: 1` — сохранить текущий срок настройки: час от `VisualSnapshot.created_at`. Повторное открытие и проверка селектора его не продлевают. Сохранённый план не зависит от этого временного снимка; после истечения можно загрузить новый.
- `keep_latest_results: 2` — защищать два последних запуска со статусами `completed` или `completed_with_errors` отдельно для каждого `(job_public_id, plan_hash)`. Порядок — `started_at`, затем UUID. Если подходящих запусков меньше, защищаются все. Это защита комплекта результата; HTML и готовые файлы выгрузок сохраняются по своим срокам.
- `automatic_enabled: false` — по умолчанию новая очистка не запускается автоматически. Можно получить предварительный просмотр и явно выполнить выбранное удаление. Включение автоматической очистки — отдельная правка политики с проверкой её версии. Уже работающая очистка временных визуальных снимков сохраняет прежнее поведение.

Дни означают интервалы по 24 часа в UTC, а не календарные даты зоны расписания. Кандидат удовлетворяет `finished_at <= evaluated_at - days`; у незавершённого запуска срок не начинается. Для `html_days`, `result_days`, `export_days` допустимы целые числа от 1 до 3650 или `null` («без удаления по возрасту»). `keep_latest_results` — от 2 до 100; час визуального снимка в первой версии фиксирован. При двух конечных сроках `result_days` не может быть меньше `html_days` или `export_days`. Неизвестные поля, ноль и отрицательные числа дают HTTP 400 `invalid_retention_policy`.

Истечение срока означает право включить объект в очистку, а не гарантию немедленного освобождения диска. До фактической очистки состояние остаётся `available`. Для зависших запусков без `finished_at` автоматического удаления нет: сначала штатная отмена/завершение, затем отсчёт срока. При нехватке места сбор получает понятную ошибку хранилища; экстренное удаление защищённых результатов не разрешается.

### Сохранение сравнения и закрепление

Помимо последних двух результатов владелец может закрепить любой терминальный запуск: `results` защищает комплект результата, `all` — дополнительно HTML и уже созданные выгрузки. Закрепление не создаёт новую выгрузку и не возвращает уже удалённый файл. Снятие закрепления не удаляет данные немедленно: нужен новый предварительный просмотр или следующий проход включённой политики.

Клиент перед длительным хранением сравнения закрепляет **обе** стороны. Просмотр сравнения и его курсор сами по себе не являются бессрочным закреплением. Пока обе стороны сохранены, очистка HTML не изменяет значения, счётчики полноты, метки `added`/`not_seen`/`not_checked`, строки без SKU и Evidence EXT-002. После удаления старого комплекта попытка сравнения даёт HTTP 410 `comparison_data_expired` с UUID недоступной стороны, а не сравнение с пустой таблицей. Проверка владельца выполняется раньше проверки срока: чужой UUID по-прежнему даёт HTTP 404.

Evidence в предпросмотре и результате содержит `html_availability: "available" | "purging" | "expired" | "missing"` соответствующего снимка. `expired` означает управляемую очистку, `missing` — неожиданное отсутствие файла, обнаруженное при чтении. Метаданные, URL, хеш, дата загрузки, локатор, исходное и нормализованное значение Evidence остаются. Очистка HTML запрещает повторное извлечение из старого снимка; новый сбор загружает страницу заново. Сервис чтения управляемо удалённого HTML возвращает `snapshot_content_expired` (HTTP 410 для ошибок API). Отдельного нового HTTP-маршрута чтения основного HTML этот этап не вводит. Наличие Evidence не обещает наличие полного HTML.

### Защита выполняемой работы

Проверки обязательны и при предварительном просмотре, и непосредственно перед каждой порцией удаления:

- Полностью защищены `exploring`, `awaiting_confirmation`, `running`, `pausing`, `paused`, `cancelling`, независимо от возраста. Пауза не делает запуск архивным.
- Терминальный статус недостаточен, если остались задачи `pending`, `leased`, `running`, `retry_wait` или незакрытые попытки. Сначала сверка REL-001; очистка не исправляет противоречивое состояние удалением задач.
- Защищены текущие закрепления и последние два подходящих результата. Пересчёт и создание нового запуска сериализуются общей блокировкой задания. Версии плана, закреплённые расписанием, и история `ScheduledOccurrence`, включая пропуски, не удаляются.
- Экспорт, сравнение, порционное чтение результата и чтение HTML получают короткую возобновляемую аренду на используемые данные: до пяти минут, с проверкой перед продолжением работы. Очистка получает несовместимую аренду. Она не держит блокировку PostgreSQL во время сетевого вызова к media_api; истечение аренды требует повторной проверки перед записью результата операции. Между запросами разных страниц таблицы аренда не удерживается: клиент может получить явный HTTP 410 на следующую порцию.
- Создание закрепления и начало очистки проверяют одно состояние под блокировкой: победило закрепление — удаление пропускается; уже началась очистка — закрепление возвращает HTTP 409 `cleanup_in_progress`. Ни один путь не сообщает об успешной защите уже удаляемых данных.
- Повторное сообщение Celery после очистки не создаёт записи заново. До отдельного удаления задания сохраняются `Run`, ключи идемпотентности `Task`, номера попыток, терминальные статусы и счётчики ошибок. Их сокращение и очистка подробных журналов не входят в этот этап.

Для `VisualSnapshot` сохраняется часовая граница доступности. Короткая действующая операция проверки/предложения плана защищает строку от физического удаления до окончания её аренды, но не продлевает право начать новую проверку после часа. Запоздалый загрузчик не может восстановить удалённую строку.

### API политики и закреплений

Все пути относительны к `/api/scout/`. Новые операции требуют аутентификации, владения объектами и `scout_view` для чтения, дополнительно `scout_configure` для изменения, закрепления и удаления. Администратор этим API не обходит ограничение владельца. Общесистемная очистка чужих данных — отдельная операторская задача.

- `GET retention/policy/` — HTTP 200, текущие значения и `version`, для первого чтения предлагаемые значения и `version: 1`.
- `PATCH retention/policy/` — частичная правка с обязательным `expected_version`; HTTP 200 с новой версией, HTTP 409 `retention_policy_changed` при конфликте. Правка инвалидирует ещё не запущенные просмотры старой версии. Уменьшение срока не удаляет данные в самом запросе.
- `GET runs/{run_public_id}/retention/` — политика, `results_availability`, `html_availability` как сводка с учётом смешанного наличия файлов, даты пригодности к очистке, закрепление и массив причин защиты. Для результатов состояния `available`, `purging`, `expired`; для HTML дополнительно `partial` и `missing`. Сохранённые итоговые количества не подменяются нулями после очистки.
- `PUT runs/{run_public_id}/retention/hold/` — тело `{"scope":"results","expected_version":1}`, обязательный заголовок `Idempotency-Key` с UUID, HTTP 200 с закреплением и его новой версией. Версия относится к закреплению запуска, исходное отсутствие имеет версию 1. Повторная доставка той же операции с тем же ключом идемпотентности возвращает исходный ответ; другое тело даёт HTTP 409 `idempotency_conflict`.
- `DELETE runs/{run_public_id}/retention/hold/` — тело с `expected_version` и такой же обязательный заголовок `Idempotency-Key`; HTTP 200 с отсутствующим закреплением и новой версией. HTTP 409 `retention_hold_changed` при конфликте. Закрепить нетерминальный запуск нельзя: HTTP 409 `run_not_terminal` (он уже защищён своим состоянием). Для `all` в ответе перечисляются уже недоступные части; HTTP 410 `run_data_expired`, если удалён сам комплект результата.

Пример политики после явного включения:

```json
{
  "version": 2,
  "automatic_enabled": true,
  "html_days": 30,
  "result_days": 365,
  "export_days": 7,
  "visual_snapshot_hours": 1,
  "keep_latest_results": 2
}
```

### Предварительный просмотр удаления

`POST retention/previews/` формирует неизменяемый перечень кандидатов, HTTP 201. Пример запроса:

```json
{
  "policy_version": 2,
  "job_public_id": "98c94e32-54c8-49c6-8ba1-d5dc09109db4",
  "scopes": ["html", "results", "exports"]
}
```

Без `job_public_id` выборка ограничена всеми объектами текущего владельца. `visual_snapshots` разрешён только без фильтра задания: у временного снимка ещё нет задания. Произвольные пути, UUID чужих владельцев, дата в будущем и принудительное игнорирование защиты не принимаются. `evaluated_at` определяет сервер один раз в UTC. Получение просмотра не меняет файлы, записи, сроки, счётчики и защиту; уже существующая часовая очистка визуальных снимков может независимо сделать его устаревшим.

Ответ включает `preview_public_id`, `policy_version`, `evaluated_at`, `expires_at` (15 минут), `manifest_hash`, `executable`, `totals`, `protected`, `warnings`. `totals` содержит уникальные количества `runs_with_result_deletion`, `records`, `evidence`, `html_files`, `export_files`, `visual_snapshots`, `file_bytes_reclaimable`, `visual_body_bytes`, `database_bytes_estimate`. Размер БД может быть `null`: число строк не выдаётся за немедленно освобождаемые байты PostgreSQL. `protected` группирует объекты по причинам `active_run`, `open_tasks`, `latest_results`, `hold`, `operation_in_progress`, `shared_blob`. Один объект учитывается в totals один раз даже при выборе нескольких scopes.

`GET retention/previews/{preview_public_id}/items/?limit=50&cursor=...` выдаёт кандидатов и исключённые объекты порциями (limit 1–200). Элемент содержит UUID объекта и запуска при наличии, тип, причину выбора/защиты, границу срока, точные количества затрагиваемых строк и известные байты. Пути файлов, HTML, значения полей, секреты, подписанные URL и сведения о чужих ссылках не возвращаются. При общем файле показывается только `shared_blob` без чужих UUID и количества владельцев.

`file_bytes_reclaimable` считает каждый физический файл один раз после проверки всех ссылок. Если размер или принадлежность файла не удалось подтвердить, оценка равна `null`, добавляется предупреждение, а затронутый элемент имеет `executable: false`. Остальной просмотр можно пересоздать без недоступного scope; нельзя скрыто исключить неизвестные файлы и подтвердить завышенный объём. Удаление результата явно показывает потерю сравнения этого запуска (`comparison_will_expire: true`), число Evidence, какие выгрузки будут удалены и какие HTML-файлы останутся до своего срока.

`executable` всего просмотра равен `false`, если хотя бы один кандидат нельзя безопасно проверить; POST выполнения отвечает HTTP 409 `cleanup_preview_not_executable`. Защищённые объекты не являются кандидатами и сами по себе не запрещают исполнение остального перечня. Пустой исполнимый просмотр допустим: задание завершится с нулевыми числами. Курсоры просмотра и задания привязаны к UUID родителя, владельцу и порядку элементов, чужой курсор даёт HTTP 400 `invalid_cursor` без раскрытия содержимого.

### Выполнение и повторы

`POST retention/cleanups/` принимает `preview_public_id`, `manifest_hash` и `idempotency_key` (UUID). HTTP 202 возвращает `cleanup_public_id` и `status: "queued"`. Подтверждение относится только к сохранённому перечню. Добавлять новые объекты из более свежей выборки запрещено. Ключ привязан к владельцу и телу запроса: повтор возвращает тот же UUID, другое тело с тем же ключом даёт HTTP 409 `idempotency_conflict`.

При принятии POST истёкший просмотр даёт HTTP 409 `cleanup_preview_expired`; изменённая политика или состояние кандидатов — HTTP 409 `cleanup_preview_changed` с предложением пересчитать просмотр. Неверный хеш — HTTP 400 `invalid_manifest`. При недоступности проверки хранилища — HTTP 503 `storage_unavailable`, удаления ещё нет. Повтор уже принятого запроса возвращает существующее задание и после истечения просмотра. Изменения после HTTP 202 отражаются в состоянии задания и пропусках элементов, а не в недоставляемом клиенту HTTP-ответе фоновой задачи.

`GET retention/cleanups/{cleanup_public_id}/` возвращает HTTP 200, состояние `queued`, `running`, `completed`, `completed_with_errors`, числа `deleted`, `skipped`, `failed`, `pending` по типам, реально удалённые байты файлов и коды ошибок. Подробности доступны через `GET retention/cleanups/{cleanup_public_id}/items/?limit=50&cursor=...`. Пауза/отмена уже начатой очистки и восстановление удалённых данных в первую версию не входят. Падение процесса восстанавливает то же задание; ручная повторная доставка не создаёт второе.

Очистка выполняется малыми порциями (не больше 200 удаляемых строк или файлов на задачу Celery) в существующей очереди `scout`; большой комплект результата разбивается на порции дочерних строк, а не удаляется одним каскадом. Она уступает выполняемому сбору: новые порции не начинают удаление при занятом слоте сбора, уже начатая короткая порция заканчивает безопасный этап. Beat каждые 30 секунд сохраняет существующую сверку и возобновляет незавершённые операции очистки. При `automatic_enabled: true` один раз за дату UTC владельца создаётся системный просмотр/задание с той же политикой и защитой; первый проход после простоя выполняется один раз, пропущенные дни не создают серию очисток. Его подтверждение — включённая версия политики, состояние фиксируется в журнале с `trigger: "automatic"`.

Перед порцией повторно проверяются владение, версия политики, состояние запуска, закрепления, аренды и общие ссылки. Новая защита после постановки даёт `skipped` с причиной, а не расширение прав удаления. После изменения политики ещё не начатые элементы также пропускаются с `policy_changed`; начатое физическое удаление завершается согласованно. Журнал хранит исходный перечень и фактический результат; пропуск не считается успешным освобождением места.

### PostgreSQL и файлы: порядок очистки

HTML очищается без удаления `PageSnapshot`. Под блокировкой общего хеша сервер проверяет **все** ссылки и действующих читателей/писателей, записывает намерение удаления и переводит разрешённые ссылки в `purging`. После коммита удаляет файл и фиксирует `expired` с датой очистки. Загрузка такого же HTML использует ту же блокировку: она либо успевает добавить защищённую ссылку до выбора, либо после удаления создаёт файл заново и отмечает новый снимок доступным. Старые очищенные ссылки остаются `expired`, даже если файл позднее появился для другого запуска. Общий файл не удаляется, пока хотя бы одна ссылка защищает именно HTML или не достигла своего срока. Защита только комплекта результата (`results`, последние два запуска) не продлевает срок HTML. Одной проверки существования файла без блокировки с записью недостаточно. Незавершённое намерение удаления исключает конкурирующую запись этого хеша и после истечения аренды: сначала восстановление намерения с проверкой поколения операции, затем новый писатель. Иначе запоздалая попытка могла бы удалить заново созданный файл.

Комплект результата сначала получает `purging`: новые чтения и выгрузки запрещены явной ошибкой HTTP 410 `run_data_expired`, сравнение — HTTP 410 `comparison_data_expired` с UUID недоступной стороны. После окончания уже выданных аренд удаляются все его `Record` и Evidence, затем фиксируется `expired`. Даже если строки удаляются порциями, частичный результат не становится видимым. Метаданные снимков, UUID запуска, финальные счётчики, полнота, план, история расписания и идемпотентность задач остаются. Это не `Run.delete()` и не `Job.delete()`. Подробные журналы, резервные копии и удаление самого задания — отдельные политики.

После удаления комплекта все связанные выгрузки подлежат удалению независимо от собственного возраста: иначе JSON продолжит содержать удалённые записи и Evidence. Такие файлы включаются в предварительный просмотр как обязательная зависимость scope `results`. У уже выданной ссылки нет гарантии мгновенного отзыва: подписанный URL действует до удаления файла либо истечения подписи. Задание не считается завершённым, пока оставшиеся выгрузки не удалены; сбой media_api оставляет видимую ошибку и повторную попытку. Это очистка по срокам, а не обещание атомарного стирания всех копий.

Файлы выгрузок удаляются только через `MediaClient.delete`, с проверкой результата/отсутствия через его интерфейс. Физический объект, на который указывают несколько старых `ExportArtifact`, очищается один раз только после проверки всех ссылок; нельзя удалить общий старый путь по возрасту одной строки. Новая реализация использует неизменяемые пути с UUID артефакта. Недоступность media_api не считается отсутствием файла. Новая выгрузка не перезаписывает удаляемый путь.

Намерение удаления хранится в PostgreSQL до подтверждения файловой операции; повтор после сбоя между удалением файла и обновлением БД трактует подтверждённое отсутствие как успех. При ошибке остаются `purging`, код ошибки и возможность безопасно повторить операцию. Состояние очистки не сообщает `expired` до успешного завершения соответствующего удаления. Непредвиденное отсутствие HTML отмечается `missing` и диагностируется отдельно. Произвольное сканирование и удаление осиротевших файлов кэша, временных `.partial` и общих каталогов в этот этап не входят.

Локальное удаление допускает только нормализованный путь внутри корня снимков, отклоняет выход через `..`, абсолютный путь, символическую ссылку или Windows junction. На media стороне используется только закреплённый путь артефакта в пространстве Scout. Ни пользователь, ни сообщение Celery не передают путь для удаления: задача содержит UUID операции, перечень и пути читаются из проверенного состояния. В журнале нет HTML, значений Evidence, паролей прокси, токенов или подписанных ссылок.

### Совместимость, приёмка и передача

Новые поля доступности добавляются к существующим ответам, форматы значений DATA-001 и SKU SPEC-001 не меняются. Для старых строк до внедрения очистки исходное состояние считается `available`, но чтение проверяет наличие файла; миграция не помечает их задним числом удалёнными. Сервер сохраняет итоговые счётчики до удаления строк. Для очищенного комплекта выдача records, JSON/CSV и сравнения отвечает явным HTTP 410, а компактный статус и история запусков остаются читаемыми. Очистка не меняет `Run.status`, `stop_reason` или полноту: завершённый полный сбор после истечения срока не становится частичным.

На каталоге SPEC-001 выполнить два сбора (цена 1250.00 → 1350.00, два URL одного SKU, новый SKU и строка без SKU), третий запуск и частичный вариант. Для проверок возраста менять тестовое время, не ждать реальные месяцы. До реализации задача остаётся открытой. Условия приёмки:

1. Предварительный просмотр не изменяет данные; числа строк, уникальных файлов и известных байтов совпадают с контрольным набором. Проверены точная граница срока, UTC, `null`, неверные поля, конфликт версии, чужие UUID, срок просмотра и повторный ключ.
2. После очистки HTML оба результата и все Evidence сохраняются; сравнение до/после совпадает по содержанию, кроме добавленной доступности HTML. JSON/CSV можно получить заново. Проверены общий хеш между запусками и владельцами, конкурентная загрузка и повторное появление тех же байтов.
3. После третьего запуска два последних результата защищены отдельно для каждого хеша плана. Старый закреплённый результат сохраняется. Снятие защиты требует нового просмотра; истечение срока доступности не продлевается чтением.
4. Удаление старого незащищённого комплекта удаляет его записи, Evidence и выгрузки, но оставляет историю и итоговые количества; чтение и сравнение отвечают HTTP 410. Запоздалые задачи не создают дубли, назначенная дата расписания после перезапуска не создаёт новый запуск.
5. Активный, ожидающий подтверждения, приостановленный и отменяемый сборы защищены. Проверены открытая задача у терминального запуска, экспорт/сравнение во время очистки, закрепление после просмотра и перед стартом порции, смена политики и аренда, истёкшая после падения процесса.
6. После удаления выгрузки старый файл не отдаётся, новая выгрузка получает другой UUID/путь и те же данные в старом и типизированном форматах. Проверены общий старый путь, 404 и отказ media_api, сбои до/после файлового удаления и повторные Celery-сообщения.
7. На живых PostgreSQL, Celery, Beat и media_api зафиксированы время порции, объём удалённых файлов, влияние на сбор из 200 страниц и восстановление очистки после перезапуска. Отдельно проверены часовые снимки настройки, опасные пути и отсутствие секретов в API/логах/задачах.

FRONTEND получает доступность HTML/результата, причины защиты, закрепление обеих сторон сравнения, предварительный просмотр объёма и потерь и состояние задания очистки. Экраны и клиентская реализация — отдельное поручение. Для воспроизведения живой серверной проверки служит [retention_live_check.py](../checks/retention_live_check.py): из корня проекта запустить `virtual_env/python/Scripts/python.exe modules/scout/checks/retention_live_check.py`. Скрипт создаёт собственную PostgreSQL, брокер, кэш HTML и media-каталог, запускает Django, worker и Beat, аварийно завершает только свой проверочный worker и удаляет свою БД после проверки. Реквизиты берёт из локальной конфигурации; в отчёт они не попадают. В рабочем проекте перед перезапуском служб требуется применить `ergoms api migrate scout 0014`.

## ANTI-001/ANTI-002 — обнаружение страниц проверки

Общий загрузчик HTML, XML и robots проверяет `cf-mitigated: challenge` и известные HTML-признаки блокирующих страниц. HTML проверяется по первым 64 КиБ. Совпадение с распознанным видом проверки возвращает `cloudflare_challenge`, `yandex_captcha` или `captcha_required`. Обычная HTTP-ошибка обрабатывается по правилам загрузчика.

Страница проверки не попадает в снимки и записи. Ошибка окончательная для загрузки, а новые загрузки запуска прекращаются. Полученные записи и Evidence доступны в частичном результате. Клиент использует прежние поля `error.detail`, `error_summary` и `stop_reason`.
